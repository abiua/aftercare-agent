# P5 局部补查消融预登记

2026-11-11。状态：受控入口已实现，尚无本消融的真实模型结果。此计划补充聊天改造第十项；不能用已有三阶段单 Agent 与多 Agent 的整体比较替代单变量消融。

## 问题和比较

检查多 Agent 核验发现具体争议后，局部补查是否带来额外的纠错收益，以及增加多少调用、耗时与估算费用。比较两个独立评测臂：`multi` 与 `multi_no_recheck`。均运行同一独立事实调查、独立政策分析及反例核验。只在首轮核验请求合法局部补查之后产生处理差异。

关闭补查的臂保存请求、争议主张与未解决问题，转人工；不得将争议方案直接发布为可批准结论。模型在首轮看到的原始输入、提示、工具和预算不因消融改变，不提前告诉模型补查被关闭。允许最终费用和实际调用数不同，因为这正是待测结果。

## 输入与公平性

先使用现有 `DAMAGE-ORDINARY` 与 `DAMAGE-TWO-LINE-PACKAGE-CONFLICT` 受控样本验证机制，分别报告。两臂冻结相同的原始消息、图像摘要、业务事实、政策版本、决策时间及证据投影，并固定模型注册表、每臂调用与费用上限。每个评测臂具有独立运行记录、检查点和账本，不共享模型推理或未核实结论。

机制验证通过后，实际模型消融另行冻结有来源的复杂样本；不把控制模型脚本输出冒充真实模型结果。现有 v3 付费门禁只允许原三臂，不自动接纳消融臂。真实执行前需有明确的新消融 campaign 与同输入绑定，但不改变现有普通案及历史报告。

## 验收用例

1. 有效补查请求：两臂首次事实/政策/核验输入一致；完整臂仅重查指定角色，关闭臂零补查调用、零第二轮核验，明确转人工。
2. 不需要补查：两臂业务输出一致，不为制造差异强行补查。
3. 非法或越范围补查：两臂均拒绝，不计作消融收益。
4. 预算不足、调用超时或交付未知：维持现有预算与对账规则，保留未完成结果；不在另一臂复用检查点，不偷偷重试。
5. 重复执行、错计划或错臂恢复：不会重复产生模型调用，也不能用原三臂或另一消融的结果充数。
6. 普通聊天、客户 API 和生产配置无法选择关闭补查；现有默认三臂、旧 manifest 与历史评测继续可读。

## 结果如何解释

先报告全部计划行和运行状态，以及补查请求/实际执行/被关闭的次数、候选动作、人工处理、调用数、活动耗时与估算费用。独立复核者在看到两臂结果前判断原始案例；之后逐项评估补查是否纠正错误或引入错误。没有独立判断时，纠错收益和可接受率保持不可测，不把“成功调用补查”算作“纠错成功”。

关闭补查可能更早转人工，这不能单凭完成率被解释为更差决策。应同时比较安全处理、问题是否解决及资源成本。普通案与复杂案分别汇报，失败和未知不剔除。若没有观察到补查请求，只能报告本次未触发待检验机制。

上述补查实验仅隔离局部补查因素；顺序传递对照的后续实现见文末。去掉反例核验仍未实现，不据此推断整套多 Agent 的全部收益来源。

## 首轮独立取证与顺序传递对照

新增test-only入口 `ChatEvaluationRunner(..., sequential_claims_ablation=True)`，清单 `chat-eval-multi-sequential-claims-ablation-v1` 包含multi与multi_sequential_claims。后者事实角色完成后，将其结构化主张提供给政策角色；政策角色仍须用自己的工具取证，不继承事实角色的可引用证据权限。原始输入、角色工具、调用/费用上限、反例核验及局部补查保持相同。该改变同时引入顺序依赖，因此不能解读为纯并行收益，延迟需单列。不可与关闭补查合并，不影响默认三臂、强单或付费入口。

真实SQLite runner/AgentService受控验证普通与双行冲突两案四臂：普通每臂5次、复杂每臂7次，共24次fixture attempts。复杂两臂都执行一次事实补查和第二轮核验；审计确认只有顺序组policy接收到完整fact主张ID，policy工具集合不变，每案scope和预算相同。重放无新调用；默认服务真实start拒绝，持久化复杂实验失去能力后在读取检查点或调用模型前拒绝。root运行runner与graph相关30项通过。没有PostgreSQL或真实模型结果，不计算独立质量收益。
