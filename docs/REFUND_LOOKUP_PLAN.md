# POL08 原退款执行记录定位

2026-11-10，待实现。POL08 要求「同一退款请求已有处理记录时返回该记录，复用原有流程」。现有执行端的重复处理保护已单独验收。现有退款进度页读的是订单账本，账本中另一笔退款无法证明客户要查的原请求。此次增加在授权订单范围内按编号读取既有退款执行记录的路径。

## 标识与权限

- 唯一标识采用账本 `Execution.id`，即页面显示的「退款执行编号」。专用输入字段接受完整的 UUID 文本，去掉首尾空白后按标准形式匹配。金额、订单号、工单号、支付幂等键、时间、列表第一笔和模拟回执编号均不用于定位。
- 在退款进度助手的自由文本中，只接受明确标签「退款执行编号」或「退款执行记录编号」后紧跟的完整 UUID，可带冒号。一般描述或孤立 UUID 不自动解释成执行编号。相同编号重复出现按同一目标处理。出现两个不同编号，或运行补充说明和工单原描述各指定不同编号时，提示只选择一笔。显式标签后的格式无效时提示更正，避免回退成对该笔退款的判断。
- 通过现有认证及 `_case` 加 `_order` 做归属校验。专用入口仅用于 `refund_status` 工单。按工单的已授权订单限定账本，匹配 `action=REFUND` 且 `Execution.id` 完全一致。另一个订单上的执行记录即使也属于当前客户，仍不属于本次查询范围。同单换发也不匹配。不得按编号先从全库取记录再判断归属。
- 查询读同一业务快照，只投影允许字段。响应不含案件内部关联、提案、审批、行明细、原业务键、原回执对象或尝试查找的失败编号。不调用支付查询或对账，不写工单、审批、执行账本、幂等记录或余额。

## HTTP 契约

`GET /api/cases/{case_id}/refund-lookup?execution_id=<UUID>`，只读且 `Cache-Control: no-store`。前端缺编号时直接显示澄清提示，不发请求。服务端错误沿用 `{"detail":{"code":"…","message":"…"}}`。

| HTTP | 返回码 | 触发条件 |
| --- | --- | --- |
| 200 | `FOUND` | 在本工单授权订单的退款账本精确找到一笔，返回下列投影。 |
| 401 | `AUTH_REQUIRED` | 登录凭据缺失、无效或已停用。 |
| 404 | `NOT_FOUND` | 工单不存在或客户无权访问。已授权工单中的编号未找到、属于另一订单或对应换发时，同样使用统一 404。响应不回显所试编号，不区分这些未命中原因。 |
| 422 | `VALIDATION_ERROR` | 必填查询参数缺失。 |
| 422 | `INVALID_REFUND_EXECUTION_ID` | 参数不是单个完整执行 UUID，含空白输入、截断编号或拼接多个编号。 |
| 422 | `REFUND_LOOKUP_INTENT_REQUIRED` | 工单已通过归属校验，但售后类型不是退款进度。 |

重复的 `execution_id` 参数不可静默取最后一个。若 API 收到多值，返回同一 `INVALID_REFUND_EXECUTION_ID`，由页面提示选择一笔。前端使用已有错误提示机制展示业务说明。

成功响应示例字段如下。

```json
{
  "schema_version": "ac-v1",
  "status": "FOUND",
  "execution": {
    "id": "1b17965e-8ecd-44f2-a983-482e334af445",
    "status": "SUCCEEDED",
    "amount_cents": 39800,
    "created_at": "2026-11-10T08:00:00+00:00",
    "receipt_confirmed": true
  }
}
```

`execution.status` 取本地账本的 `SUCCEEDED`、`FAILED`、`SUBMITTING` 或 `UNKNOWN`，无法识别的旧状态以待核对文案显示。`amount_cents` 是该次执行登记金额，整数分。`created_at` 是账本记录创建时间。`receipt_confirmed=true` 表示本地模拟账本记录了确定的处理状态及可确认的模拟回执。失败也可有确认失败的模拟回执。未知或提交中不标为确认。即使成功且有模拟回执，也只说明此系统内的模拟处理结果。客户实际到账须另行核对。

## 页面和助手

- 「方案与回执」的退款进度区域保留订单级汇总和历史累计。下方明确区分「订单的退款执行记录」与「查询指定退款」。已有退款行显示完整的执行编号并可点选核对。无编号、多编号或格式有误时请客户补齐或确认，单行账本也不自动定位。查询结果只展示所选一笔，清空后回到订单总览。
- 助手从既有持久化的运行补充说明及工单描述确定是否指定目标。取本次已授权账本，复用同一精确匹配和安全投影。发布字段新增 `refund_lookup`，形状为 `{status, execution}`。`status` 为 `FOUND`、`REFERENCE_REQUIRED`、`AMBIGUOUS_REFERENCE`、`INVALID_REFERENCE` 或 `NOT_FOUND`，只有 `FOUND` 的 `execution` 非空。
- 有明确目标时，找到、未找到或需要澄清均走确定性状态答复，无需请求模型。保持 `STATUS_ONLY` 语义，`action=null`、`lines=[]`。无指定目标时可保留既有订单汇总，但明确说明要定位某一笔需要执行编号。通用输出中的 `ledger` 仍是订单级数据；定向答复只给匹配记录或空范围，不以其他执行替代。历史累计在两个范围中均为单独的订单级数字。
- `read_case_facts` 保持空参数。若角色处理退款进度，其已验证事实包括 `refund_lookup` 与明确的账本范围。角色无任意编号查询工具，也不能将客户提到的编号或订单总览升格成已核实的原请求。即使模型声称已执行，状态查询也只发布程序生成的记录和说明。
- POL08 只在已授权账本精确绑定目标退款时标记前提 `MET`，`scope.execution_ids` 只有匹配记录的编号。若未找到指定记录，可报告未匹配，仍不推断是否曾在线下申请。缺编号或歧义仍缺同一请求证据。若要发布条件引用，须使用当前版本解析已选中、条件登记摘要一致的原文。POL12 在定向模式只检查所选一笔，别笔 `UNKNOWN` 不支持该笔的超时或未知前提。继续保留文档适用、条件匹配与人工语义支持三种不同证据。

## 恢复与历史兼容

两种入口共享业务解析。直接 HTTP 查询从本次授权后的同一订单快照读取，不保存选择。助手在图进入前用持久化输入和当前账本派生选择状态及安全结果，把定向查询绑定到该周期的可信摘要。恢复前和最终发布前重新认证、重读账本并从同一输入重新派生。选择、授权或匹配记录状态变化时，沿用上下文变化保护，停止发布旧结果。禁止用随机值或当前时间作为摘要字段。

已完成的历史运行只读，历史结果没有新增字段时前端照常展示。部署前已持久化的定向运行若无法证明其检查点绑定了本次目标，按缺绑定转人工；通用旧运行保持原摘要口径。方案复用现有账本主键、工单描述和运行补充说明，无新增数据库字段。

## 验收矩阵

| 范围 | 必须观测 |
| --- | --- |
| 标识与归属 | 同单两笔分别精确读取。猜测编号、同客户另一订单、他人订单、同单换发得到一致的 404，不回显编号。匿名 401，跨客户工单 404。缺、空、截断、多值各按契约返回。 |
| 表达与澄清 | 明确标签命中；自由文本孤立 UUID、订单号、回执编号不自动匹配。单笔账本的无编号请求仍提示确认。重复同一编号与两个不同编号分开测试。 |
| 状态与展示 | 各账本状态保留。模拟回执缺失或存在时显示正确。空账本不解释为未申请。订单历史累计不作为单笔金额或到账证据。 |
| 工具和引用 | 工具拒绝任意查询参数。定向结果不展示同单其他记录。POL08 只引用已匹配执行编号，POL12 不能用同单别笔的未知状态支持目标。带目标的规则路径不发模型调用。 |
| 恢复与安全 | 模拟同案版本不变时执行状态更新，旧检查点不能发布旧单笔结果。查询、澄清和重放前后核对执行、支付、方案、审批、工单版本及余额不变。 |
| 页面 | 在受控浏览器覆盖输入、选择已有行、清空、无结果与错误提示。真实浏览器和真实 PG 如另行验收，分别留存对应证据。 |
