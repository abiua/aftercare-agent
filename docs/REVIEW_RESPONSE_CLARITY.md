# 发布内容与角色证据复核

本次把开发复核包中的实际发布内容与当前代码逐项对照。复核包区分了模型角色笔记、程序发布内容和检查结果。下文的修复建议依据可核对的业务字段。回复是否解决了用户的问题，仍由人工复核者判断。

依据见 [人工复核包](HUMAN_REVIEW_PACK.md#待审样本) 和 [开发复核记录](../data/review/development-review.json)。

## DEV-HR-02 错发缺证时仍未直接回答拍什么

**仍存在。** 规则已根据当前适用的政策版本读取所需材料类型，并从中扣除已提供的类型。现行 `POL13` 要求错发实物照和包裹标签照。已知缺证会在模型调用前暂停，所以复核包中的旧模型草案并非当前流程产生材料清单所必需的环节。当前 Graph 仍将所有 `WAITING_INPUT` 写成「请补齐所列材料后继续」。缺项保存在结构化字段中。材料页和运行页会展示缺项，但共用标签把 `LABEL` 显示成「运单或标签」，未限定为包裹标签。客户工单默认没有助手协作页，因此只改助手卡片无法覆盖客户所见的材料页。 [材料规则](../backend/src/aftercare/business/rules.py#L158) · [POL13](../backend/src/aftercare/business/seed.py#L12) · [Graph 输出与暂停](../backend/src/aftercare/intelligence/graph.py#L443) · [材料页](../frontend/src/CaseMaterials.tsx#L28) · [标签](../frontend/src/ui.tsx#L23) · [客户工单标签页](../frontend/src/CaseWorkspace.tsx#L37)

- 在 `graph.py::_output` 直接用 `eligibility.missing_materials` 生成补拍说明，明确「请上传收到的错发商品实物照片，以及包裹外部标签照片」。已交其中一类时只说仍缺的类型。保留状态、缺项代码和零模型暂停。清单由规则计算，程序可以注明适用条款 ID；标为原文引用时应携带同一业务快照里的政策版本和实际原文。
- 在材料页、运行页和评测展示统一使用「包裹标签照片」与「错发商品实物照片」。另有确定性分支 `MATERIALS_NEED_MORE`，材料审核可要求补证但未返回具体类型。该分支应展示当前审核的补证说明或提示查看审核意见，避免重列一套已齐全的照片。 [审核要求补证](../backend/src/aftercare/business/rules.py#L171) · [评测展示标签](../frontend/src/evaluationPresentation.ts#L20)
- 受控测试覆盖两类都缺、只缺 `LABEL`、材料齐全但审核要求再补。验证单 Agent 与多 Agent 的公开文字和结构化代码一致，已知缺证仍无模型调用。前端检查客户材料页能直接看到准确标签。

## DEV-HR-03 空账本没有给出查询结果

**仍存在。** 工具已经按订单退款执行记录范围报告 `ledger_result=NONE_FOUND`，并把历史累计退款和执行账本拆开。发布层却固定写「退款进度仅根据当前模拟账本反馈」。客户的处理页已有「暂无可确认的退款回执」提示，但其范围写成了「该工单」且混用「执行记录」和「回执」。退款进度场景的业务上下文实际还包括同一订单其他工单的退款执行记录。缺少回执也可能是已有执行记录的结果未知。 [业务账本范围](../backend/src/aftercare/business/service.py#L579) · [工具账本语义](../backend/src/aftercare/intelligence/graph.py#L135) · [发布说明](../backend/src/aftercare/intelligence/graph.py#L448) · [客户退款进度页](../frontend/src/CaseProcessing.tsx#L36)

- 根据可信账本分支生成公开说明。已成功查询且为空时写「在该订单的退款执行账本中未查到执行记录。是否曾申请、是否失败或是否到账，需另行核对」。有 `UNKNOWN` 或 `SUBMITTING` 记录时说明已有记录、结果待确认。历史退款累计即使大于零也单独标注为累计金额。查询失败、拒绝访问或运行无结果时保留原错误或待复核状态。客户退款进度页使用同样的查询范围与术语。
- 运行面板目前把 `output.policy_ids` 标成「引用条款」，但 `policy_ids` 在无草案时通常来自业务候选政策集合。即使 `citations` 的来源、版本和原文通过校验，校验也未判断条款前提。将候选 ID 与本次结论的证据分开显示。空账本上，`POL08` 的同一退款请求已有处理记录前提及 `POL12` 的执行超时或结果未知前提都不能由空记录建立。将它们显示为条件性查阅项或从当前结论引用中移除，保留检索与原始角色审计。账本有其他执行记录时也不能仅据数量认定是同一退款请求。 [引用校验](../backend/src/aftercare/intelligence/graph.py#L223) · [输出字段](../backend/src/aftercare/intelligence/graph.py#L467) · [运行面板引用标签](../frontend/src/RunPanel.tsx#L133) · [POL08](../data/v0.1/agent/business.json#L11000) · [POL12](../data/v0.1/agent/business.json#L11046)
- 受控测试覆盖空账本且累计为零、空账本但累计非零、存在未知或提交中执行、存在明确回执、查询错误。断言文本不把累计金额或缺失回执当作单笔执行事实，空账本不把两个条件条款标作已满足，且各分支均无新处置动作。

## DEV-HR-01 材料审核与财务审批在角色输入中仍可混淆

**部分隔离，角色事实命名仍需修复。** 材料审核由客服对当前材料版本登记，财务审批由独立审批人针对具体方案版本与内容完成。正式处理权限已分开。Graph 只把有效材料审核决定压成 `review: ["APPROVED"]`，既丢掉审核对象，也没有显式区分财务审批是否在工具读取范围内。当前提示已有来源与执行限制，但输出校验只约束结构、草案字段和引用原文；它不会判断自由文本中的「人工审批状态为已批准」。上游笔记已从角色间消息投影移除，当前发布的 `output.notes` 也使用程序文本。这两层隔离都保留。原始角色笔记仍进入事件，流式片段在内部运行页有临时预览。客户页面隐藏该面板，但拥有工单读取权限的客户可通过运行事件 API 读取相应审计，因此不能把原始笔记当成已核验业务事实。 [材料审核权限和版本](../backend/src/aftercare/business/service.py#L786) · [独立审批记录](../backend/src/aftercare/business/service.py#L1203) · [工具角色事实](../backend/src/aftercare/intelligence/graph.py#L135) · [角色间消息投影](../backend/src/aftercare/intelligence/graph.py#L249) · [角色事件](../backend/src/aftercare/intelligence/graph.py#L425) · [事件读取](../backend/src/aftercare/intelligence/service.py#L641) · [运行页草稿及证据](../frontend/src/RunPanel.tsx#L124)

- 将工具字段 `review` 改为带类型、决定和材料版本的 `material_review`。当前工具未查财务审批时，显式给出财务审批的 `NOT_CHECKED` 状态。若业务确实要回答是否已审批，则由同一授权快照提供范围明确的有效审批状态，绑定具体方案版本及过期状态；`NOT_CHECKED` 与已查询后未发现有效审批分别表示。提示明确材料审核结果只能说明材料已审核，资格结果只能说明能否提交，执行账本才反映登记的执行结果。
- 对已核验材料、允许提出方案、已形成草案分别使用可区分的发布说明。财务审批和外部执行均从各自记录取值。合适时展示已确认的订单行可退上限，同时标为上限；若没有拟退金额，继续保留空动作。不要直接发布角色的自由文本作为最终说明。
- 运行草稿和角色证据界面标明「模型生成，未核验」。若客户 API 产品边界要求只看结论，按角色投影事件，保留每个事件的原序号和分页语义，避免因隐藏片段改变重连游标。内部原始审计保留。
- 用假模型返回复核包里的错误审批断言。断言工具事实只把 `APPROVED` 绑定到当前材料版本，程序发布内容无财务批准声明，也未创建财务审批或执行。补测历史材料版本、未读取财务审批、已过期审批和当前有效审批；后两项仅在引入可信审批快照时加入。对可见草稿或角色事件做标签测试；若收窄客户 API，测同页数量、序号和 SSE 重连。

本次仅静态审查现有代码及冻结的开发报告。未运行数据库、浏览器或付费模型，未修改应用代码、历史实验、评测答案或人工标注。历史模型笔记仍是原运行记录。修复后可先复跑对应的受控回归，再对新发布文本做人工复核。
