# 多 Agent 优势量化：架构重构与顺序执行计划

日期：2026-11-13（第三版）。状态：待实施的设计与计划，不是完成报告。本文不含实现代码。
依据：官方 τ²-bench Retail 首轮结果（[评测说明](TAU_OFFICIAL_EVALUATION.md)）、120 条原始对话与私有角色记录的逐题核对、官方政策原文、现有运行器与产品架构（[架构](ARCHITECTURE.md)、[聊天改造计划](CHAT_REDESIGN_PLAN.md)）。

## 0. 目标与约束

- **目标**：展示多 Agent 相对普通 Agent 的优势，并给出可复现的量化数字。
- **付费约束**：付费调用越少越好。只在官方测试集上跑一个批次，每题每组只跑一次，不做训练集上的付费迭代。
- **由此带来的做法**：开发阶段全部依靠免费手段（首轮记录的离线回放、单元测试、程序化构造的样本）；付费只发生在一次很小的接线检查、一个离线审查基准和最终批次上。

## 1. 首轮结果的重新归因

### 1.1 三组的失败构成

按"失败时发生了什么"重新统计首轮 120 条记录：

| 失败类型 | 强单 | 三阶段 | 多 Agent |
| --- | ---: | ---: | ---: |
| 成功 | 29 | 25 | 25 |
| 认证阶段客户退出（零工具调用） | 4 | 5 | 5 |
| 转人工 | 6 | 7 | 6 |
| 未采取行动，客户退出 | 1 | 0 | 0 |
| 执行了写操作但结果不符 | **0** | 3 | 3 |
| 预算耗尽 | 0 | 0 | 1 |

（强单的 29 含任务 79 的技术补跑；该题首轮异常，不计入失败类型。）

### 1.2 两个关键结论

**结论一：强单 Agent 没有写错过，它的失败全部是"放弃"。**
强单的 11 次失败里，4 次是认证走不通，6 次是转人工，1 次是没有行动。没有一次是执行了错误的写操作。这意味着：

- 在强模型上，"审查写操作、拦住错误"几乎没有可改进的空间。
- 真正的空间在"不该放弃的时候没有放弃"。首轮多 Agent 仅有的两次独胜（任务 64、111）正是这一类：强单转了人工或没行动，多 Agent 找到了可行的做法并完成。

**结论二：旧多 Agent 的 3 次写错，是顾问机制自己引入的。**
三阶段和多 Agent 各有 3 次写错（任务 38、60，以及 42 或 74），强单一次没有。每轮常驻的顾问笔记没有减少错误，反而制造了错误。

### 1.3 对前两版分析的更正

核对官方政策原文后，有两处需要更正：

- **任务 42**：政策原文确有一句"Exchange or modify order tools can only be called once per order"。政策角色的否决有字面依据，不是凭空编造。但同一份政策在"修改商品"一节又写明只有修改商品这一个动作限一次，并且订单状态仍为 pending 时可以修改；官方环境也允许先改地址再改商品。所以这是**政策歧义下取了更保守的解释**。前两版提出的"程序核对政策原文是否存在"拦不住这种情况，需要另一条规则（见 3.2 的规则 4）。
- **任务 38**：政策要求取消原因必须由客户在两个选项中确认。政策角色让客户二选一符合政策；失分是因为官方目标与客户实际确认的原因不同。这一题不应算作多 Agent 的设计缺陷。

### 1.4 其他已核实的事实

- 评测跑的是 `scripts/tau_official_agents.py`，与产品的调查图（`investigation/graph.py`）没有共享代码。
- 首轮多 Agent 共 354 次顾问调用（三个角色各 118 次）；任务 101 的 48 次预算里顾问占 27 次。
- 首轮每题一次；强单与多 Agent 结果不同的 8 题为 6 比 2，精确 McNemar 检验 p≈0.29。
- 首轮执行者提示词里有一句"可以在一轮中批量调用工具"，与官方政策"一次只能调用一个工具"相冲突。
- 首轮记录中，Agent 对客户的回复带有一层 JSON 包装（形如 `{"message": "..."}`）。来源尚未核对，列入阶段 2 的检查项。

## 2. 要证明的主张

每组每题只跑一次，所以"多次运行更稳定"无法测量，从主张中删除。按 1.2 的结论，主张改为围绕"少放弃"和"省钱"两条主线。

| 编号 | 主张 | 指标 | 对照 | 数据来源 |
| --- | --- | --- | --- | --- |
| H1 少放弃 | 独立审查把本可完成的请求从"转人工或不行动"里救回来，且不增加写错 | 放弃失败数、错误写入数 | M1 对 S1 | 最终批次 |
| H2 成功更多 | 多 Agent 的成功题数高于强单 Agent | 成功题数 | M1 对 S1 | 最终批次 |
| H3 更省钱 | 便宜模型执行、强模型把关，成功数接近全强模型，费用更低 | 成功题数、每成功一题的费用 | M2 对 S1、对 S1c | 最终批次 |
| H4 审查可靠 | 审查 Agent 能挽回不该放弃的请求、拦住错误的写操作，且很少误判 | 挽回率、拦截率、两类误判率 | 审查 Agent 自身 | 离线基准 E1 |
| H5 独立上下文是关键 | 效果来自独立审查，而不是多花了几次调用 | 同 H4、H1 的指标 | 审查 Agent 对 单 Agent 自检 | E1 为主，最终批次为辅 |

**把握与证据强度的预期（未经实验验证）：**

- H4、H5 在离线基准上样本量可以做到几百，结论最扎实，费用只有几美元。**这是整个展示的主要证据。**
- H3 的费用差来自模型单价（执行者用半价模型），比较确定；成功数是否接近要看便宜模型的能力。
- H1、H2 在 40 题、每题一次的条件下只能给出方向性结论。按首轮的波动幅度，M1 对 S1 的差距需要达到约 6 题以上，成对检验才可能显著。

## 3. 目标架构

一个执行内核，四层能力逐层叠加；评测和产品共用同一个内核，对照组只差开关和模型。

```
客户消息
   │
   ▼
┌──────────────────────────────────────────────────────────────┐
│ 第 1 层  对话执行者                                           │
│          拥有对话、工具循环和所有对客户的回复                 │
├──────────────────────────────────────────────────────────────┤
│ 第 2 层  程序护栏（不调用模型；除 S0 外所有组都开启）         │
│          认证状态机 · 写操作前置条件 · 单步单工具             │
├──────────────────────────────────────────────────────────────┤
│ 第 3 层  独立审查 Agent（独立上下文，两个触发时机）           │
│          提交审查：写操作之前                                 │
│          放弃审查：转人工、拒绝请求之前                       │
├──────────────────────────────────────────────────────────────┤
│ 第 4 层  按需专家 Agent（程序信号触发）                       │
│          政策分析 · 事实对账 · 图片证据（仅产品）             │
└──────────────────────────────────────────────────────────────┘
   │
   ▼
提交后端（可替换）
   · 评测：直接执行官方写工具
   · 产品：生成决策快照 → 客服审核 → 独立审批 → 模拟执行
```

### 3.1 一步的完整链路

1. 执行者读取对话和工具结果，生成下一步：回复客户、调用读工具、提出写操作，或提出转人工。
2. 程序护栏检查这一步。不合格时把原因作为内部反馈交还执行者，重新生成一次。
3. 如果这一步是写操作，触发**提交审查**；如果是转人工或拒绝客户的请求，触发**放弃审查**。其余情况直接放行。
4. 审查 Agent 需要专项取证时，或程序信号命中时，调用**按需专家**，专家结果返回给发起方。
5. 审查结论为放行则执行；为修改则把意见交还执行者，重新生成一次，之后直接放行。
6. 写操作交给提交后端。

### 3.2 让多 Agent 真正起作用的设计规则

1. **审查 Agent 看不到执行者的推理过程。** 它只拿到这一步的提议、公开对话、政策和工具结果，从零独立判断。这是它能发现执行者盲点的原因，也是与"单 Agent 自检"的唯一区别。
2. **放弃审查是主要价值来源。** 执行者提出转人工或拒绝时，审查 Agent 独立列出客户在本次对话中的全部请求，逐项判断是否在能力范围内，并给出一个具体可行的下一步（例如"先完成退货部分""告诉客户两种做法只能选一种，请客户选择"）。这一条直接对应首轮强单的 7 次放弃失败。
3. **提交审查默认放行。** 只在三种情况下要求修改：参数无法追溯到客户原话或工具结果；选定的商品不满足客户提出的某项属性；缺少客户的明确确认。
4. **政策有歧义时不否决。** 判断顺序为：程序护栏已确认前置条件成立的，审查 Agent 不得以政策解释为由否决；具体章节的规则优先于通用规则；工具本身会校验合法性的，交给工具裁决。任何情况下，政策解释上的疑虑都不能成为转人工的理由。这一条对应任务 42。
5. **审查只在两个时机触发。** 预计每题 1 到 4 次审查调用，首轮为每题约 9 次顾问调用。
6. **不同角色可以用不同模型。** 执行者承担大部分对话轮次，可用半价模型；审查和专家调用次数少，用强模型。
7. **执行者是唯一的决策者和发言者。** 审查意见和专家结果都以内部反馈的形式一次性提供，用完即弃，不以 system 消息身份常驻。
8. **护栏和审查规则只从公开政策推导**，每条都注明对应的政策条文。

## 4. 量化设计

### 4.1 对照组

| 代号 | 名称 | 配置 | 是否新跑 |
| --- | --- | --- | --- |
| S0 | 普通单 Agent | 官方默认 Agent 加首轮的通用提示，强模型 | **不新跑**，直接引用首轮强单结果（29/40） |
| S1 | 强单 Agent | 第 1、2 层，强模型 | 新跑 |
| S2 | 单 Agent 自检 | S1，加上在同样两个时机、在执行者自己的上下文里复查一次 | 新跑 |
| S1c | 便宜单 Agent | 第 1、2 层，半价模型 | 新跑 |
| M1 | 多 Agent（同模型） | 第 1 到 4 层，全部强模型 | 新跑 |
| M2 | 多 Agent（混合模型） | 第 1 到 4 层，半价执行者 + 强审查与专家 | 新跑 |

强模型为 `gpt-6.1-sol`；半价模型建议用 `gpt-6.1-terra`（首轮的模拟客户模型，单价为前者的一半，价格表和接口都已就绪，见决策点 D5）。

**两个标题数字，分开报告：**

- **多 Agent 的净贡献 = M1 对 S1**（并列给出 M1 对 S2）。两组都带程序护栏，差别只在有没有其他 Agent。
- **相对普通 Agent 的总提升 = M1 对 S0**。这个数字更大，但包含程序护栏的贡献，且 S0 来自另一个批次。报告必须拆开写明各部分各占多少。

### 4.2 指标

每条试验先归入一个结局，再计算指标。归类由脚本根据官方评分记录和工具调用序列完成。

| 结局 | 判定方式 |
| --- | --- |
| 成功 | 官方得分为 1 |
| 错误写入 | 失败，且执行过至少一次写操作 |
| 转人工 | 失败，未执行写操作，调用了转人工 |
| 认证未过 | 失败，零工具调用或认证工具未成功 |
| 未行动 | 失败，已认证，未写、未转人工 |
| 未完成 | 预算耗尽、超时或技术异常，计入分母 |

| 指标 | 计算方式 | 对应主张 |
| --- | --- | --- |
| 成功题数与成功率 | 成功 ÷ 40，固定分母 | H2、H3 |
| 放弃失败数 | 转人工 + 未行动 | H1 |
| 错误写入数 | 见上表 | H1 的约束条件 |
| 每成功一题的费用 | 该组已记录费用 ÷ 成功题数，含所有 Agent、模拟客户和评审 | H3 |
| 调用次数与时延 | 每题的 Agent 调用次数、耗时中位数 | 成本的另一面 |
| 挽回率 | 离线基准中，被审查 Agent 正确驳回的"不该放弃"样本占比 | H4 |
| 拦截率 | 离线基准中，被正确要求修改的"错误写操作"样本占比 | H4 |
| 误判率 | 离线基准中，正确的写操作被要求修改、正确的转人工被驳回的占比 | H4 |

### 4.3 两个实验

**E1 审查离线基准（主要证据，费用很低）**

- **原理**：把审查 Agent 当作一个分类器来评测。给它一批已知对错的"提议"，看它判对多少。不需要模拟客户，每个样本只需一次模型调用。
- **样本来源**：首轮 120 条记录。
  - 正确的写操作：官方得分为 1 的运行中的写操作及其之前的对话。
  - 错误的写操作：对正确样本做程序化改错。改错类型预先固定：换成同商品的另一个款式、换成另一件商品的编号、改掉取消原因、换成不属于该用户的支付方式、截掉客户确认的那一轮。
  - 不该放弃：把成功运行的对话截到写操作之前，把这一步替换成转人工提议。另加首轮真实发生的放弃失败。
  - 正确的放弃：首轮中官方得分为 1 且以转人工结束的运行。这类样本很少，如实报告数量。
- **去重与划分**：同一题在三组里的重复样本按题目合并。按题号的固定规则把题目分成开发半和保留半；提示词只在开发半上调试，报告的数字只来自保留半。
- **对比对象**：审查 Agent 与单 Agent 自检跑同一批保留样本。自检的输入额外包含执行者的完整上下文。
- **产出数字**：挽回率、拦截率、两类误判率，各带置信区间；审查 Agent 与自检的差值。

**E2 最终批次（一次性）**

- 测试集 40 题 × 5 个新跑的组 × 每题 1 次 = 200 次试验。
- 同一题的各组使用相同的随机种子和相同的模拟客户配置。
- 只跑一次。不因分数高低重跑；技术异常的补跑规则沿用首轮。

### 4.4 统计与判定

- **成对比较**：M1 对 S1、M1 对 S2、M2 对 S1c 各列出"仅前者成功、仅后者成功、都成功、都失败"的题数，报告精确 McNemar 检验的 p 值。
- **如实陈述检出能力**：40 题、每题一次，只有两组结果不同的题数明显偏向一方（例如 7 比 1）时才会显著。达不到时，结论写成"方向一致，未达显著"。
- **E1** 用二项比例的置信区间，审查 Agent 与自检的差值用成对检验。
- **判定标准在阶段 1 冻结**（建议值，见决策点 D6）：

| 主张 | 成立的条件 |
| --- | --- |
| H1 | M1 的放弃失败数少于 S1，且 M1 的错误写入数不多于 S1 加 1 |
| H2 | M1 的成功题数多于 S1；同时报告是否显著 |
| H3 | M2 的成功题数不少于 S1 减 2，且每成功一题的费用低于 S1；或 M2 的成功题数比 S1c 多 3 题以上 |
| H4 | 保留半上挽回率与拦截率均不低于 70%，两类误判率均不高于 10% |
| H5 | 保留半上审查 Agent 的挽回率或拦截率高于自检，差值的 95% 区间不含 0 |

## 5. 顺序执行计划

前一阶段未达标，不进入下一阶段。阶段 0 到 3、5、6 不产生付费调用；阶段 4 含 E1（数美元）；阶段 7 是唯一的评测批次。

### 阶段 0　冻结现状与失败归类

**原理**：重构期间所有的免费验证都依赖首轮记录，必须先把它们固定下来，并把失败整理成可以直接转成测试用例的清单。

**做法**
1. 处理工作树里约 237 个未提交的改动。按主题分批提交；确实不提交的，列出清单和原因。给首轮评测对应的代码状态打标签。
2. 写一个归类脚本，按 4.2 的结局定义把 120 条记录自动归类，输出应与 1.1 的表一致。这个脚本之后直接用于最终批次的统计。
3. 为每条失败补一行人工备注：直接原因、涉及的政策条文、属于哪一层应当解决的问题。
4. 把首轮记录登记为只读夹具，记录哈希。

**注意事项**
- 归类脚本读取的是评测侧数据（含官方评分），产出只用于统计和测试，不能进入任何 Agent 的输入。
- 首轮记录不得改写；补充信息另存。

**产出**：基线标签；归类脚本；失败归类表。
**完成标准**：脚本输出与 1.1 一致；首轮文件哈希未变。

### 阶段 1　架构契约与实验预注册

**原理**：先把各层之间传递什么数据定死，后续各层才能独立开发和测试。先把主张和判定标准写死，结论才不会被结果倒推。

**做法**
1. **架构决策记录**：第 3 节的内容，加第 7 节各决策点的结论。
2. **五个契约**，每个写明字段含义、谁产生、谁消费、失败时的默认行为：
   - **工具端口**：把环境的工具分成读、写、认证、转人工四类，内核只按类别处理。
   - **步骤提议**：执行者这一步想做什么。写操作的每个参数带"来源"标注（来自哪句客户原话或哪条工具结果）。
   - **审查结论**：放行或修改；修改时必须给出具体问题和建议的下一步。没有"否决并转人工"这个选项。
   - **专家请求与结果**：要回答的一个具体问题、允许的只读工具、结构化的结论与依据。
   - **运行轨迹**：每层每次调用的角色、阶段、模型、输入摘要、输出、用量和费用。
3. **预注册文档**：第 2 节的主张、4.1 的对照组、4.2 的结局与指标定义、4.3 的 E1 改错类型与划分规则、4.4 的判定标准。提交入库后不再修改；确需修改时保留修改记录。
4. **核对调查图的数据结构**：阅读 `investigation/orchestration.py` 中主张、反例、核验结果的定义，判断能否直接作为专家结果的格式（决策点 D1）。

**注意事项**
- 契约只描述数据和责任，不绑定某个模型或某个环境。
- 审查结论里刻意不设"否决"，是为了从结构上杜绝任务 42 那种"审查导致放弃"。

**产出**：架构决策记录；契约文档；预注册文档。
**完成标准**：六个对照组仅凭"开启哪几层、各角色用哪个模型"就能完整描述；D1、D3、D6 有结论。

### 阶段 2　执行内核与运行器改造

**原理**：评测和产品必须跑同一份 Agent 逻辑，评测结果才能代表产品。现有运行器把"角色"和"模型名"绑在一起，无法支持一组内使用两个模型，需要先解开。

**链路**
官方编排器 → 薄适配器（把官方工具归类后接到工具端口）→ 内核（执行者循环，逐层调用护栏、审查、专家）→ 运行器的传输层（预算预留、调用、结算、记账）。

**做法**
1. **新建内核模块**，放在后端包内。内核只依赖工具端口和模型调用接口，不引用官方评测库，也不引用业务服务。
2. **薄适配器**：`scripts/tau_official_agents.py` 只保留"官方工具归类"和"把内核包装成官方 Agent 接口"两件事。
3. **运行器记账改造**：
   - 调用的角色归属改为由调用方显式声明（执行者、审查、专家、自检、模拟客户、评审），不再由模型名反推。否则半价模型作为执行者时会被记到模拟客户名下。
   - 每个角色可以单独配置模型和推理强度。
   - 预算仍是"每题 Agent 侧总调用数"一个上限，所有 Agent 角色共用，保持各组可比。
   - 批次清单里记录每组的层开关和各角色的模型。
4. **首轮配置保留**：旧的每轮顾问实现原样保留为历史配置，只用于复现首轮，不再参与新批次。
5. **执行者提示词清理**：删除"可以批量调用工具"这句与政策冲突的话。这一改动只进入 S1 及之后的组；S0 引用首轮结果，不受影响。
6. **核对回复的 JSON 包装**：查明首轮记录里 `{"message": ...}` 是模型输出、运行器产物，还是官方库的行为，并确认模拟客户实际看到的文本。如果客户看到的是带包装的文本，需要修正，并在报告中说明首轮受此影响。
7. **离线回放测试**：用首轮记录里的模型回复序列作为替身，驱动内核跑一遍，检查在 S0 配置下产生的工具调用序列与首轮强单逐步一致。

**注意事项**
- 回放验证的是"内核没有改变行为"，不验证模型质量。
- 预算和记账是首轮评测可信度的基础，改造后原有的预算并发、未结算请求、固定分母等离线测试必须全部通过。
- 这一阶段不改任何提示词以外的行为。

**产出**：内核模块；薄适配器；改造后的运行器与记账；回放测试。
**完成标准**：回放逐步一致；原有适配器、预算、评分接线测试全部通过；JSON 包装问题有结论。

### 阶段 3　程序护栏（第 2 层）

**原理**：能用确定性规则判断的事，不交给模型。护栏不调用模型，只读取对话记录和已有的工具结果，因此零成本、可穷举测试。它对除 S0 外的所有组生效，作用是清除共同瓶颈，让架构差异有机会显现。

**链路**
执行者生成一步 → 护栏按类别检查 → 通过则继续；不通过则生成一条内部反馈（写明哪条规则、缺什么、建议怎么做），执行者重新生成一次 → 第二次仍不通过时，按该规则的"兜底动作"处理并记录。

**护栏清单**（每条都来自官方政策原文）

| 护栏 | 政策依据 | 检查方式 | 不通过时的反馈 |
| --- | --- | --- | --- |
| 认证状态机 | 必须通过邮箱或姓名加邮编定位用户，客户直接提供用户 ID 也不行 | 维护状态：未认证、邮箱已试、姓名邮编已试、已认证。未认证时只允许认证工具和对客户回复 | 提示尚未认证，并列出还没试过的认证方式 |
| 认证阶段的回复 | 同上 | 未认证时，对客户的回复必须同时包含两种认证方式的请求；不允许在此阶段转人工 | 提示改为同时给出两条路 |
| 单用户 | 一次对话只服务一个用户 | 读写工具的用户、订单参数必须属于已认证用户（订单归属从已有的工具结果判断） | 提示该对象不属于当前用户 |
| 单步单工具 | 一次最多调用一个工具，调用工具时不同时回复客户 | 一步里有多个工具调用时只保留第一个 | 无需反馈，直接截断并记录 |
| 订单状态 | 取消和修改要求 pending，退货和换货要求 delivered，且操作前应查看状态 | 对话里必须已有该订单的详情结果，且其中状态符合要求 | 没查过则提示先查；状态不符则提示该操作不可行 |
| 商品替换 | 只能换成同一商品的另一个有货款式 | 新旧编号数量一致；新编号出现在已查到的同一商品的款式列表里且有货 | 没查过商品则提示先查；不符则指出具体哪一项 |
| 支付方式 | 差价或退款的支付方式须属于该用户；退货退款只能退回原支付方式或已有礼品卡；礼品卡余额须足够；改支付方式须与原方式不同 | 对照已查到的用户资料和订单支付记录 | 指出具体哪一项不符 |
| 取消原因 | 只接受两个固定原因 | 参数必须是两者之一 | 提示只有两个可选值 |
| 确认环节 | 写操作前必须列出细节并得到客户明确同意 | 结构性检查：写操作之前，执行者最近一次对客户的回复之后必须有一条客户消息；且执行者不能在首次提到该操作的同一步就执行 | 提示先向客户列出细节并等待确认 |

**做法**
1. 每条护栏写成独立的规则，输入是"对话记录 + 本步提议"，输出是通过或一条反馈。
2. 为每条规则写"应通过"和"应不通过"两类用例。用例优先从首轮记录中截取真实片段。
3. 用首轮记录做一次全量回放统计：在首轮成功的运行上，护栏不通过的次数应为零或接近零。如果不为零，逐条检查是规则太严还是首轮碰巧违规。
4. 写一张"护栏与政策条文对照表"。

**注意事项**
- **不做语义判断。** "客户是否真的同意了""客户的请求是否超出范围"交给第 3 层。护栏只查结构和数据。
- **肯定结论有效力。** 护栏确认"订单状态为 pending"后，这个结论会随提议一起交给审查 Agent，审查 Agent 不得再以政策解释否决（规则 4）。
- **认证不做"拆用户名"**，除非决策点 D4 另有结论。
- **护栏解决不了客户主动退出。** 首轮认证失败的直接原因是模拟客户收到拒绝后退出。护栏能保证 Agent 给出两条路，但客户是否配合取决于模拟客户，效果只能在最终批次里看到。
- 护栏的依据必须是政策条文。看过测试题之后很容易写出针对某一题的规则，对照表就是用来防止这一点的。

**产出**：护栏模块；规则用例；对照表；首轮回放的误拦统计。
**完成标准**：每条规则两类用例齐全；首轮成功运行上的误拦逐条有解释；首轮"认证阶段客户退出"的对话片段回放时会触发认证相关规则。

### 阶段 4　独立审查 Agent（第 3 层）与 E1

**原理**：执行者在长对话里会形成自己的思路，并顺着它走下去；让它自己复查，它倾向于确认自己。一个只看到"提议和证据"、看不到推理过程的独立 Agent，没有这个惯性。首轮数据显示强模型的问题集中在"放弃得太早"，所以审查的重点是放弃，其次才是写操作。

**链路**
触发（写操作，或转人工，或对客户的回复被识别为拒绝请求）→ 组装审查输入 → 审查 Agent 给出结构化结论 → 程序校验结论的格式和引用 → 放行，或把意见作为内部反馈交给执行者重新生成一次 → 直接放行。

**审查输入**（两种审查相同）
- 公开对话：客户与执行者之间的全部消息，以及全部工具调用和结果。
- 政策全文。
- 本步提议，以及护栏对本步已确认的事实。
- 不包含：执行者的推理过程、此前的审查意见、专家的中间讨论。

**放弃审查的方法**
1. 让审查 Agent 先独立列出客户在对话中提出过的每一个请求，以及每个请求的当前状态（已完成、未处理、已拒绝）。
2. 对每个未完成的请求，判断政策允许的处理方式里有没有能用的：整单取消、修改地址、修改支付方式、换款式、退货、换货、提供信息。
3. 输出二选一：
   - **放行**：每个未完成的请求都确实超出能力范围，且已经向客户说明过可用的替代做法。
   - **修改**：给出一个具体的下一步，例如"订单中有两件可以退货，先向客户确认并办理退货"或"换货和退货在同一订单上只能选一种，把这一点告诉客户并请其选择"。
4. "拒绝请求"的识别：先用程序规则筛出候选（对客户的回复里出现无法办理一类的表述，且对话将要结束或客户刚提出新请求），再由审查 Agent 判断。宁可少触发，不为了识别拒绝而增加一次模型调用。

**提交审查的方法**
1. 逐个参数核对来源：订单号、商品编号、新款式、支付方式、取消原因、地址，各自对应客户的哪句话或哪条工具结果。
2. 对商品选择，列出客户提过的每一项属性要求，逐项对照所选款式。如果有多个款式都满足，或客户有某项要求没有说明，结论为"修改：请客户在这几个款式中选择"，不替客户选。
3. 核对客户的确认是否针对当前这组细节（如果确认之后细节又变了，需要重新确认）。
4. 其余情况一律放行。政策解释上的疑虑按规则 4 处理，不构成修改理由。

**做法**
1. 实现两种审查及其结构化输出；格式不合规、超时、预算不足时默认放行并记录原因。
2. 实现 **S2 的单 Agent 自检**：同样的触发时机、同样的审查指令、同样的输出格式，唯一区别是在执行者自己的上下文里进行（能看到自己的全部推理）。这样 S2 与 M1 的差别就只有"上下文是否独立"。
3. 审查意见交给执行者时使用内部反馈的形式，措辞为建议而非命令，只在紧接着的一次重新生成中可见。
4. **搭建 E1**：
   - 样本构造脚本按 4.3 的规则从首轮记录生成四类样本，记录每个样本的来源题号、类型和改错方式。
   - 按题号固定规则划分开发半和保留半。
   - 在开发半上调试审查提示词。这一步有少量付费调用。
   - 冻结提示词后，在保留半上各跑一遍审查 Agent 和自检，计算指标。
5. 每个保留半样本只跑一次，不重跑挑选。

**注意事项**
- **检查点**：如果保留半上审查 Agent 不优于自检，或误判率超过判定标准，停在这一阶段改进设计。此时还没有花最终批次的钱。
- **程序化改错的局限**：改出来的错误是"已知类型"，比真实错误容易识别。报告里要写明这一点。
- **"不该放弃"样本的局限**：把成功对话截断后换成转人工，审查 Agent 面对的是"明显有路可走"的情况，比真实的放弃容易。首轮真实的放弃失败只有十来条，单独列出它们的结果。
- **样本来自测试集的首轮记录。** 这些题目会在最终批次里再次出现。开发半与保留半的划分只能防止提示词过拟合到具体样本，不能使 E1 与最终批次相互独立。报告中写明。
- **不让审查变成第二个执行者**：审查 Agent 不调用写工具，不直接对客户说话，每次触发只输出一次结论。
- **调用预算**：审查与执行者共用每题 48 次的上限。按每题 1 到 4 次审查估算不会重现任务 101 的情况，但运行轨迹里要单独统计审查调用占比。

**产出**：审查模块；自检模块；E1 的构造脚本、样本清单和结果。
**完成标准**：单元测试覆盖默认放行、只重试一次、非触发步骤零调用、审查输入不含执行者推理；E1 在保留半上给出 H4、H5 的数字。

### 阶段 5　按需专家 Agent（第 4 层）与模型配置

**原理**：有些判断需要集中查阅多条记录（跨多个订单、多件商品核对），放在执行者的主对话里会拉长上下文、分散注意力。把它交给一个上下文干净、只做这一件事的专家，执行者只接收结论。专家必须按需调用，否则会重蹈首轮每轮常驻的覆辙。

**链路**
触发信号命中（程序判断）或审查 Agent 提出需要 → 生成专家请求（一个具体问题 + 允许的只读工具 + 范围限定）→ 专家在独立上下文中查询并作答 → 结构化结果返回给发起方 → 记入运行轨迹。

**触发信号**（全部由程序从对话记录判断）
- 已认证用户有多个订单，且客户的请求没有指明订单号。
- 一次请求涉及三件及以上商品，或涉及两个及以上订单。
- 客户陈述与工具结果不一致（例如客户说已签收，订单状态是 pending）。
- 客户提出带约束的选择（最便宜的、与原来同价的、某预算以内的）。
- 产品环境中：有图片证据。

**两类专家**
- **事实对账**：回答"满足客户这些条件的候选项有哪些"。输出候选清单，每个候选注明满足和不满足的条件、价格差。不做推荐，不替客户选。
- **政策分析**：回答"某个具体做法在政策下是否可行"。输出结论、对应的政策原文、以及政策没有明确规定的部分。原文引用由程序核对是否存在。

**做法**
1. 实现触发判定和两类专家。专家只能使用读工具，参数限定在已认证用户及其订单范围内；越界请求拒绝并记录。
2. 每个专家请求最多使用固定次数的读工具调用，超过即返回已有结论。
3. 专家结果以"一次工具结果"的形式交给执行者，与其他查询结果同等对待，不带指令性措辞。
4. 按决策点 D1 的结论选择结果格式。
5. **配置 M2 和 S1c**：执行者用半价模型，审查和专家用强模型。在离线替身下确认六个组的配置都能跑通，记账的角色归属正确。
6. 按阶段 2 的回放方式统计触发率：在首轮 40 题的对话上，触发信号命中的题目比例应明显低于一半。

**注意事项**
- 专家的收益在 40 题的批次里很难单独量化。它的定位是"第 3 层的取证工具"和"产品里复杂案的入口"，不单独设主张。
- 专家调用计入每题 48 次的总预算。
- 如果触发率过高，说明信号定义太宽，回到信号清单收紧，而不是提高预算。
- 半价模型的工具调用能力尚未验证，留到阶段 7 的接线检查确认（决策点 D5）。

**产出**：专家模块；触发规则文档；六组配置。
**完成标准**：无信号的对话专家调用为零；越界查询被拒；六组在离线替身下全部跑通且记账正确。

### 阶段 6　接入产品

**原理**：项目要展示的是"这个售后产品里的多 Agent"，而不是一个只在评测里存在的适配器。内核接入产品后，评测数字才对应到真实运行的代码。

**链路**
客户聊天消息 → 现有的会话分析与分流 → 内核（工具端口对接业务只读工具）→ 提交后端生成决策快照 → 现有的客服审核、客户确认、独立审批、模拟执行。

**做法**
1. **产品侧工具端口**：把现有的业务只读工具（订单、材料、退款记录、政策检索）归类后接入。
2. **产品侧提交后端**：内核提出的"写操作"在产品里不直接执行，而是生成候选决策快照。审查 Agent 的结论作为快照的一部分保存，供客服查看。
3. **调查图的定位**（决策点 D2）：保留现有调查图，作为第 4 层在复杂案信号出现时调用的深度调查；普通案由内核直接完成。现有的分流规则继续决定普通与复杂。
4. **早期三角色图**（`intelligence/graph.py`）标记为遗留路径，旧工单工作台继续可用。
5. **处理 5 项聊天回归**（见[工程验证记录](TAU_OFFICIAL_ENGINEERING_REVIEW.md)）：
   - "强单 Agent 工具输入预算超限后工具被移除"直接影响第 1 层，优先处理：先确认提示词与工具定义各占多少预算，再决定是压缩内容还是调整上限。
   - 其余 4 项先写明预期行为，再决定改代码还是改断言。
6. **准备一条产品演示案例**：一条复杂案，展示审查 Agent 驳回一次不当的转人工或要求修正一个参数。这是演示，不计入统计。

**注意事项**
- 不改动审批、执行账本、幂等和恢复机制。
- 新旧检查点不混用：内核路径使用新的图版本标识，旧运行仍按旧版本读取。
- 不为了通过测试而修改业务断言。
- 如果希望更早拿到评测数字，本阶段可以放到阶段 7 之后。代价是评测时内核还没有在产品里运行过，报告中需要写明。

**产出**：产品侧适配；回归处理记录；演示案例；更新后的[架构文档](ARCHITECTURE.md)。
**完成标准**：三个演示场景（[演示指南](DEMO_GUIDE.md)）仍可完整走通；5 项回归各有结论；后端非数据库回归无新增失败。

### 阶段 7　一次性付费评测（需授权）

**原理**：只有一次机会，所以先确认一切就绪，再冻结，再跑。跑完之后只分析，不调整。

**做法**
1. **评测脚本升级**：支持五个新组的排程、每组的层开关与角色模型、4.2 的结局归类、成对比较、费用按角色汇总。
2. **接线检查**（约 $1）：每组在训练集里取 1 到 2 题实跑，只检查：能正常结束、各角色的调用都被正确记账、审查和专家确实被触发过、半价模型能完成工具调用。**只看是否跑通，不看得分，不据此调整提示词。**
3. **冻结**：内核、护栏、审查与专家的提示词、各组配置、预算上限、归类脚本、预注册文档，全部记录哈希并写入批次清单。
4. **运行**：测试集 40 题 × 5 组，新目录，不覆盖首轮。并发、超时、每题预算沿用首轮设置。
5. **异常处理**：技术异常且无官方分数的条目，按首轮规则在独立目录补跑一次；已有官方分数的条目不补跑；预算耗尽计入分母。
6. **分析**：归类脚本生成主表；成对比较与检验；E1 结果并入；逐题对照表；按预注册的判定标准给每个主张下结论。
7. **发布**：更新测试中台的摘要与视图、[评测说明](TAU_OFFICIAL_EVALUATION.md)和[失败记录](TAU_OFFICIAL_BAD_CASES.md)。

**注意事项**
- **只跑一次，结果可能不如预期。** 每题一次的结果受模拟客户随机性影响很大（首轮任务 45 就是一例）。设计已经尽量提高真实胜算，但不能保证。结果不利时照实报告，不重跑挑选；是否追加批次由你另行决定。
- 接线检查如果暴露的是程序缺陷，修复后重新检查；如果暴露的是"效果不好"，不在这里改，因为没有独立的数据可以验证改动。
- S0 引用首轮结果，与新批次不是同一次运行，主表中明确标注。
- 费用设硬上限，达到即停止，未运行的条目计入分母并标注。

**产出**：新批次的原始记录、汇总、审计；更新后的文档与测试中台。
**完成标准**：五个主张各有"成立、不成立或证据不足"的结论；原始行、官方评分与调用账本核对一致。

### 阶段 8　收尾与交付

**做法**：更新 README 的当前状态；把"首轮结果 → 失败构成分析 → 重构 → 新结果"整理成一条完整的线索；演示脚本加入阶段 6 的案例；整理一页面向展示的摘要，包含架构图、主表和三张图。
**完成标准**：每个结论都能指向代码位置和实测证据；未成立的主张与已成立的并列呈现。

## 8. 风险与已知局限

- **每题一次、只跑一个批次，结论的统计强度有限。** H1、H2 多半只能给出方向性结论。E1 是统计上更可靠的部分。
- **开发用的是测试集的首轮记录。** 没有训练集上的付费迭代，护栏和审查的设计都参考了测试集 40 题的失败情况，最终批次又在同样的 40 题上进行。因此最终成绩是"在已分析过的题目上的表现"，不能当作对新题目的泛化能力。护栏与政策条文的对照表、E1 的保留半划分可以减轻但不能消除这个问题。报告里必须写明。
- **强模型上可改进的空间有限且集中。** 首轮强单的 11 次失败里，4 次认证失败由护栏处理（所有组受益），留给多 Agent 的是 7 次放弃失败。M1 对 S1 的净优势上限大约就是这个量级，实际会更少。
- **审查可能把正确的转人工也驳回。** 有些请求确实超出能力范围，驳回会拖长对话甚至引出错误操作。E1 的误判率和最终批次的错误写入数用来监控这一点。
- **模拟客户不可控。** 认证护栏能保证 Agent 给出正确的引导，但客户是否继续配合不由 Agent 决定。
- **半价模型的能力未经验证。** H3 是否成立取决于它。
- **"相对普通 Agent 的总提升"容易被误读。** M1 对 S0 的差值包含护栏的贡献，且两者不在同一批次。必须同时给出 M1 对 S1 的净贡献。
- **调查图的复用程度尚未核对。** D1、D2 的建议基于对模块结构的阅读。
- **费用为估算。** 依据首轮单价推算，随对话长度变化。
