## 输入与评分隔离

- 运行器通过 `scripts/tau_p5_cases.py` 加载 [输入](../data/tau-p5/agent/cases.json)、基础目录和原图。模型仅接触正常聊天、持久订单事实、经审核的材料、授权工具及政策语料。图片关联以正常材料审核记录体现。
- [评分条件](../data/tau-p5/evaluation/references.json) 仅用于运行后核对。模型、工具与模拟客户均不读取此文件。输入、评分条件和基础资产由 [清单](../data/tau-p5/manifest.json) 固定。应用当前店铺有效条款，保留工具返回的版本和生效时间。POL09 适用时，减额和客户确认仍遵循独立处置批准及后续执行审批。
- 保留每次尝试的初轮产物和原始工具轨迹。用实际模型验证时，自然首轮正确记为「首轮正确，纠错未触发」。将合成错误注入验证器或用固定模型输出的回归，单独记为机制回归。

## 逐项验收

1. 记录同一调查输入摘要下的事实与政策分支标识、开始及完成时间、首次工具回执和各自结果。并行须有时间交叠证据。冻结首次可比较的主张与金额。
2. 验证分支记录具体冲突主张 ID、商品行和反证来源。随后必须执行目标工具并取得有效回执。仅提出补查、空结果、参数拒绝、查错商品、错误版本及重复原查询均不能证明局部补查。
3. 对比补查前后结果。出现被证伪的主张时，旧主张或方案标记撤销并停止对外采用。最终方案应引用补查新证据，或说明哪个约束仍未解决及为何转人工。检查 L01 超额、L02 串用材料、过期政策授权、重复退款和缺审批均无法执行。
4. 报告按订单列出初轮是否正确、冲突是否触发、目标回执是否成立、旧方案是否撤销、最终状态、人工判断及失败原因。真实运行缺任一必要证据时，保留具体未验收项。P5 实际纠错验收要求至少一次完整轨迹。
