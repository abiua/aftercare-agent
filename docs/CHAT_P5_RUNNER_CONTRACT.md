# P5 三臂聊天评测执行契约

新协议使用独立的 `chat-eval-v1` 数据、运行清单和结果目录。旧 `evaluation/runner.py`、正式 V2/V3 注册、四条件协议、历史结果和留出集继续按各自原协议解释。P5 开发包、验证包和正式留出各自登记来源、暴露历史与版本。

当前实现仅接受调用方已构造的本地 SQLite 测试聊天源，使用控制模型、`AgentService.process` 的 worker 核心和实际 P3 投影。清单记录运行时提示版本，旧实测报告仍沿用各自版本。定向测试覆盖三臂候选经业务校验、Multi 定向补查、程序门禁零调用、输入变更、图片损坏、回执变更和未知恢复。PostgreSQL/S3 需要单独实现并验证隔离适配，Celery 端到端、真实模型、跨库盲审登记和正式留出也仍需各自验收。

## 冻结与隔离

- 数据包固定客户原话及顺序、事项确认、订单行和业务事实、原图顺序与消息绑定、每个对象原始 SHA-256/字节数/类型/来源、完整原始政策版本及生效条件。登记合成或获准来源，原图字节留私有对象存储。共享视觉模式先走真实 P2 接口生成观察，保留原图和送模摘要、转换版本、尝试与观察的绑定，另记共享视觉耗时和费用。逐臂重跑视觉使用独立验收清单，报告各臂观察差异和费用，比较单位为完整流程。
- 每个 `case_id + repetition` 在无候选的测试源环境回放一次真实聊天入口。通过 `ConversationDecisions.resolve` 获取一个序列化 `DecisionScope`，固定业务时钟、客户消息水位和目录 `decision_at`。保留 `scope.input_sha256`、`dependency_sha256`、`build_input(scope).relevant_input_sha256`、原始目录摘要与完整 scope JSON 摘要。将同一冻结 scope 交给三臂，禁止独立重新冻结后把变化的决策时点删去充当同输入。运行截止时间、尝试时间和耗时使用实际运行时钟。
- 当前每臂使用独立 SQLite 文件、`eval_<执行标识>` 和 `NamespacedObjects` 隔离原图。后续 PostgreSQL 适配需要验证测试集群及 schema 的所有权，再接入隔离执行。每臂从同一个无候选源状态复制所需行和已核对的原图对象，保留业务主键、时间戳及逻辑对象键。每臂使用独立运行 ID、检查点线程、P3 决策头和尝试账本。每臂启动前及取回真实快照后核对冻结 scope 的完全一致性和对象字节摘要。复制源数据可以共享，模型输出、工具收据、审批和执行状态不跨臂。
- 跨 schema 配对摘要使用带版本的结构，由按冻结顺序排列的客户原话、原图清单及字节摘要、事项与订单行、业务事实、有效观察及来源、完整政策目录、产品范围和包括 `decision_at` 在内的业务时间组成。排除物理 schema/桶前缀、实验臂、运行/尝试 ID 和运行耗时。数据源的消息、附件、订单行和证据 ID 保持一致；需要另存实例对照时使用清单中的稳定源标识，保持其关系和版本。配对摘要用于对账和聚合，P3 快照及盲审另验精确 scope 和原图绑定。各臂产生不同证据或版本时标输入不一致，保留原行及原因。

## 启动与对照

- 从测试侧调用已有 `AgentService.start`，给定固定 `mode`、`strategy`、`expected_version`、同一 `decision_scope`、`decision_previous=None`、`graph_profile=CHAT_GRAPH_PROFILE`、每行稳定幂等键及冻结的 `legacy_agent_input.message`。明确指定 `investigation_arm` 为 `strong_single`、`single_staged`、`multi`，客服测试入口不设置 `decision_turn_id`。由真实 worker、LangGraph 检查点、工具和 P3 决策投影生成候选。真实执行清单使用已登记的实际模型传输，失败和兼容检查走实际链路。受控模型测试另记证据等级和运行清单。
- 固定模型别名、供应方模型标识、注册表和提示/图/目录版本、检索配置与语料、工具能力并集、输出/输入上限、运行截止、调用/令牌/费用上限与重试上限。核对尝试记录中的实际模型与配置。角色隔离、角色工具子集、核验保留与实际工具次数按架构执行并留证。根据 `investigation_route` 和实际阶段事件确认 `SINGLE`、`STAGED`、`MULTI`；硬门禁仍优先进入 `PROGRAM`，验证模型尝试为零并单列门禁覆盖。
- 预登记 `repetition → case → arm` 交错顺序与固定或预登记轮换顺序。先持久化全部计划行及稳定执行标识，再启动。记录开始、终态、可见候选、各失败阶段和原因；缺候选、超限、跳过、未运行及 `UNKNOWN` 都有行。恢复时按原幂等键和真实尝试账本对账，已有请求且结果未明的行保持未知，禁止无依据重发或把剩余额度转给别臂。每个计划行保留实际尝试数、已知用量、费用估算、未知用量/费用、预留，以及提交至可见、活动、排队耗时和删失标记。

## 盲审绑定与后续

当前 `BlindReviewService.assign` 只在一个测试数据库会话内读取来源和候选快照，要求每个候选 `origin=AGENT`、相同会话/事项且 `snapshot.input` 与源 scope JSON 完全相同。初判输入摘要由公开投影计算，源快照 ID 另参与来源摘要。每臂独立 schema 的快照不能直接用现有 `assign` 跨库查找；P3 同事项/版本唯一键也不允许把各臂快照当成同一业务库中的普通快照导入。

实现应扩展受信任的测试侧盲审登记入口。逐臂从原 schema 读取原始 P3 行和运行证据，验证同一精确 scope、臂与运行绑定及快照来源，复用现有公开输入和候选投影。盲审库事务只写已验证的盲任务，使用一份受控源对象映射供评审取图。保存臂和运行到盲 ID 的私有对照表。缺真实候选的行保留在运行清单；当前入口要求至少一个 AGENT 来源候选，整组无候选时单列缺可评候选，禁止补造 P3 快照。仍由既有初判封存、曝光和逐项标签顺序处理；初判前只出现同一公开输入，程序检查、客服意见和臂映射留私有。现有单 schema 入口保留原义。

首次验收需要有程序门禁、普通和复杂冲突案，核对原图、版本、三臂路径、真实尝试、失败保留及真实快照到盲审的绑定。报告按案例配对，重复行提供稳定性证据；程序零调用覆盖、人工可判率和模型质量分别汇报。消融在三臂固定后另开预登记清单，分别移除独立取证、专门反例核验或局部补查，共用业务安全门、来源和总体预算，并以实际节点事件证明变更。
