# 售后案例 v0.1

## 运行输入与验收口径

- 每案独立加载 `fixture.order`、所选商品与物流快照，再恢复初始履约、退货质检、附件和退款账本。模拟执行只修改该案例的工作副本。基表用于实体索引，案例金额采用快照中的历史行价、已分摊优惠和已退款金额。实付和余额按行及订单守恒。
- 场景编写接口带 `family`、`policy_ids` 和 `fixture.request.kind` 供验收编排。构建后，这些分类字段在评测索引里。Agent 的首条输入只给请求人、订单号和客户话语。测试适配器用快照实现业务工具，用事件模拟后续返回。事件时间晚于初始观察时点，按先后顺序投递，工具结果仅在对应请求发起后交付。初始客户话语可含多条短消息。补传附带的后续话语和请求重放由事件按时间投递。客户话语里关于仓库、客服或支付状态的描述仍由工具核验。
- `ATTACHMENT_ADDED` 记录模拟附件元数据。商品照要关联待核验订单行，包裹照关联当前订单。损坏核验结论通过 `DAMAGE_REVIEW_RESULT` 返回。数据集不含图片文件，附件标签不代表图像识别结果。
- `FULFILLMENT_RESULT` 和 `INTERCEPTION_RESULT` 分别响应仓库复查及承运商拦截。审批事件 `APPROVAL_RESULT` 按发生时点更新状态。只有已满足其他执行条件的退款才能使用批准结果。
- `resolution` 是独立批准的商家补偿记录，包含授权订单行和批准时间。部分退款先检查处置资格，再计算金额并判断是否需要金额审批。
- `RETURN_RECEIPT_RESULT` 与 `RETURN_INSPECTION_RESULT` 分别更新退件收件及质检状态。普通退货的时间窗口以首次申请为准。混合可退商品需先确认修改退货行，客服不能擅自改变申请范围。
- `REFUND_CALL_RESULT` 是对应幂等键的退款执行结果，`REFUND_QUERY_RESULT` 是原键的对账结果，`REQUEST_REPLAY` 表示同一业务请求再次提交。超时或查无记录仍保留原键。预期的支付查询和实际退款调用次数分别计数。

每个验收答案给出有序的关键动作、禁止动作和结构化终态。动作是业务检查点，工具名称可由后续实现映射。检查点可与必需的读取或日志步骤交错。所有样本均禁止盲目重试和超额退款。没有预期支付执行或查询的案例也明确禁止该动作。

`REQUEST_POLICY_APPROVAL` 专指模拟政策 POL10 的金额门槛。`APPROVAL_RESULT` 指这类场景审批的事件。后续应用可以对所有资金写入再设置统一的人审门禁。评测金额门槛时，依据 `policy_approval_required` 判断是否触发 POL10，并单独核对应用级人审流程。

| 终态字段 | 说明 |
| --- | --- |
| `status` | 本案售后流程结果 |
| `new_refund_cents` | 本案新确认入账的金额，含对账后补记的原退款 |
| `order_refunded_cents` | 初始历史退款与本案新入账之和，仅供评测内部核验 |
| `payment_calls.execute_refund` / `payment_calls.query_refund` | 实际退款调用及原键查询的精确次数 |
| `line_refunds` | 本案新入账金额的订单行分配 |
| `policy_approval_required` | 在金额边界场景核对是否触发 POL10 |
| `order_status` | 需要明确核对时的履约状态 |
| `original_refund_status` | 原幂等键在账本中的最终执行状态 |
| `proposed_refund_cents` / `excluded_fee_cents` | 尚待处理的可退金额或应剔除费用 |
| `missing_evidence` / `evidence_line_ids` | 需补齐的照片类型与相关行 |
| `eligible_line_ids` / `ineligible_line_ids` | 混合退货申请各行资格 |

答案由规则与场景逐案编写，未通过未来的 Agent 或规则引擎生成。自动测试核对分割、隔离、引用、余额、边界与关键故障预期。留出集还需人工复审后才能作为独立人工金标。
