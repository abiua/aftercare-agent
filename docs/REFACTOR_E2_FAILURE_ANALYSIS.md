# E2 失败案例与多维指标复盘

2026-11-13。只读取已保存的对话、官方评分、调用账本和代码；新增模型调用0、费用0。没有修改实现、提示词、评分或冻结文件。补跑后的最终轨迹用于案例分析；费用和耗时包括首次尝试及补跑。新增诊断是事后分析，不改预注册主张。

## 主要结论

M1（全强多Agent）比S2（强单加自检）净少成功2题：18、27、60题仅S2成功，111题仅M1成功，另36题结果相同。不能简单归因于“专家能力差”：这4条分歧轨迹都没有专家调用。明确暴露的是审查意见缺少后续落实检查、审查覆盖范围不全，以及模拟客户实际说出的需求不一致。

M1的10条失败中，6条是认证阶段结束（5、9、39、45、56、68），这些轨迹都未进入审查或专家；另外4条是18、27、32、60。专家只在8道最终成功题上调用过；这8题S2也全部成功。该现象不能证明专家有效，也不能证明专家造成M1失分。

## S2与M1逐题分歧

| 题 | 可直接观察的过程 | 归因与边界 |
|---|---|---|
| 18：坏椅子换同款 | S2原拟转人工，自检要求先解释同款换货限制并提供选项，客户选择灰色皮椅，最终成功。M1先解释限制，随后主动提供人工选项；客户坚持同款并同意转人工，独立审查放行。 | 对话引导路线不同。M1最终审查已面对“客户明确要求转人工”，不能仅凭0分认定该次放行错误；较早提供人工、未查库存和具体替代款是机会点。专家未参与。 |
| 27：同单退货与换货 | M1第一次审查要求先查防水靴，执行者确实补查；第二次要求继续说明并确认，但执行者再次输出转人工，后置程序检查仍放行，最终未办理。S2自检明确指出任一操作会改变订单状态，要求客户选优先项；客户选换靴，完成后转人工处理剩余退货，官方成功。 | 已证实的闭环缺口：修改后的动作只经过硬规则，不再检查原审查问题是否解决。第二次M1意见也没有像S2那样清楚处理“先做哪个”的约束，反而弱化了组合限制。不能只归咎执行者不听话；建议本身也须可执行。专家未参与。 |
| 60：耳机换蓝色 | S2收到客户明确说“若有多个选项，要不防水款”，选$242.92款，成功。M1客户只说换蓝、价格相同或更低，执行者保持原IPX4属性，选$226.49款，客户确认，审查放行；官方仍按$242.92不防水款判失败。 | 同任务和种子并未保证相同可见诉求。这里不能认定审查忽略了已说出的“不防水”条件，因为M1对话没有。询问多个款式是改进点，但不应让审查猜官方隐藏答案。专家未参与；约束触发词也没覆盖实际“price is the same or lower”表达。 |
| 111：笔记本地址与手表修改 | M1审查阻止过早转人工，要求回答拆单和历史地址问题；客户后来授权整单改地址，三项操作完成。S2客户始终不提供或确认纽约地址，仅授权手表修改后要求人工，最终官方失败。 | M1有可观察的积极作用，但两边客户后续授权不同，不能把整道题的成功完全归于审查。S2的手表修改有授权，不应因分类为“错误写入”就宣称该操作违规。专家均未参与。 |

第32题两组都失败：S2未完成后续事项即转人工；M1完成了两个取消，随后因客户无法接收退货邮件转人工、未完成退货。它说明同样的0分可能对应不同程度的业务完成，成功率无法表达这一点。

## 审查的具体缺口

1. **修改建议不形成待解决事项。** `engine.py`收到revise后再生成一次，只运行`post_review_guard`；合法转人工仍可通过。第27题第二次修改后又转人工是实际例子。下一版可保存“未解决问题+应满足条件”，校验修改是否回应；不能以无限重试代替闭环。
2. **审查写操作时范围过窄。** `review.py`强调默认放行，重点是参数来源、属性和确认，缺少金额算术、多个动作的先后依赖和执行后是否堵住其他请求。应交给程序的约束不宜继续只靠模型判断。
3. **关键审查失败默认放行。** M2第97题，改商品前的审查返回`fallback_reason=ValueError`，系统默认放行；先改商品导致订单状态锁定，已确认的地址修改无法再做。日志足以确认回退和动作次序问题，但只保留ValueError，无法确定是JSON格式、字段校验还是引用错误；不能编造更具体原因。对于会堵死后续操作的写入，审查不可用应暂停并转入明确的后备处理。
4. **算术没有硬校验。** M2第108题原始价格244.02+52.03+50.88应为346.93，却告知347.93；独立审查放行，官方金额断言失败。应由程序/计算工具汇总并核对。该题官方DB检查也失败，不能把金额问题说成唯一评分原因。

## 专家的问题：当前更像一次性材料整理

- 官方适配器创建`ExpertService(self.port)`，未传入读取工具执行函数。最终M1的8次专家调用、M2的18次调用，`reads`全为0。这轮并未验证专家独立取证。
- 触发主要靠词匹配、客户明确写出多个`#W`订单号、已出现的订单状态冲突。第27题“即将执行的两个动作互相影响”没有覆盖；第60题自然语言价格条件也漏掉了。
- 缓存按触发消息/订单状态等标识，不按证据版本失效。M2第36、38题专家只看到相机资料，指出其余四类商品信息缺失；之后执行者又查了四类商品，专家没有重新计算，旧结论继续加入上下文。
- 第36题执行者随后把已经买到的$193.38背包替换为$198新款，把最低订单价算成$1,135.47，错过原可达到$1,130.85的方案。专家没有重新核算完整组合，审查取消订单时也只看最后确认。这里证实了缺失的核算机会，尚不能证明旧专家意见直接造成错误。
- 第38题虽然官方失败，但客户最终明确确认的是`ordered by mistake`，评分预期为`no longer needed`。这是对话与预期动作差异，需要作为评分适配问题检查，不能直接记作专家业务判断错误。
- `grounded()`主要检查候选ID在记录中出现、政策引文存在，不保证候选的金额、条件和推荐组合正确。ID可追溯不等于整条结论已核实。

没有“去专家”“去独立审查”的同输入消融，因此本轮不能分离两者各自的净收益。

- **转人工不一定失败。** 原六类结局按成功、写入等优先归类，不是所有转人工事件计数；两者已分别列出。M2“放弃失败为0”不等于没有转人工，更不等于做对了：它还有5个写操作后失败。
- 工具报错包含合法的“账号未找到”，不能都当作接口故障。主批次技术连接异常另有6次，规则拒绝3次，均按既定规则补跑。
- M1比S2的已知总费用略低，不能笼统说多Agent在本轮一定更贵；但两者均缺计费回执，完整费用和每成功费用继续标待定。M2比S1c的已知费用高、成功数少，至少目前不支持“低成本执行加强审查更划算”。
- S1c完整每成功总费用为$0.01609，Agent部分$0.00409。费用包含成功和失败尝试；总费用另含模拟客户和裁判，不能当作真实部署的客服模型单价。
- P95使用40个耗时的最近秩第38项，补跑题累加两次耗时；这是诊断性新增指标，不含排队、不是服务压测延迟。
- S2要求修改发生在7题，最终5题成功；M1在6题中4题成功；M2在4题中3题成功。这是修改后的最终结局，**不是因果纠错率**，也不是误拦率。

## Claude计划里的审查质量指标

项目保存的架构计划和E1报告确实还规定了挽回、拦截和误判指标，不能被端到端成功率替代：

| E1冻结标签指标 | 独立审查 | 自检 |
|---|---:|---:|
| 错误写入拦截率 | 43/45，95.6% | 43/45，95.6% |
| 对应的标注错误漏检率 | 2/45，4.4% | 2/45，4.4% |
| 不当转人工挽回率 | 14/14，100% | 14/14，100% |
| 正确写入误拦率 | 1/24，4.2% | 0/24，0% |
| 正确转人工误拦率 | 0/3 | 0/3 |

这是旧审查提示词、构造样本和冻结标签下的历史结果，不能当成当前E2提示词的可靠率。两条“删除确认”错误标签有更早授权等争议，3条正确转人工对照也太少。E1没有证明独立审查优于自检。完整限制见[E1结果](REFACTOR_E1_RESULTS.md)。

E2现有数据无法可靠给出逐条审查的真实误拦率/漏检率，因为候选动作没有完整独立标签；当前普通/复杂分层、关键事实遗漏率、政策引用正确率、局部补查纠错率、客服一致率/独立可接受率也未形成完整核验结果。不能用“审查allow数”“修改后成功数”冒充这些指标。高并发吞吐和队列等待同样未由本次评测测量。

## 建议顺序（本次未实施）

1. 先用现有轨迹做免费回归：第27题修改后仍转人工、第97题先改商品锁死地址、第108题算术错误、第36题保留原商品与最低组合价。
2. 补齐请求清单、动作依赖和金额校验；审查报错记录具体阶段，关键写入使用明确的后备处理。
3. 专家改为面向具体缺口的查询与重算，证据变动使旧结论失效；不要单纯增加调用频率。
4. 评测侧记录模型实际可见的客户约束、每个子请求是否完成及失败原因。先离线人工核对已存轨迹，不让模型接触隐藏标准答案，不改本轮分数。
5. 如以后需要验证因果，再另行预注册同一可见对话下的自检/独立审查、专家消融；本次不启动任何新付费运行。
