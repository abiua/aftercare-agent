# P3 决策快照与确认接线

现有 Recommendation 提供一个动作、订单行、引用及冲突。图输出可以作为候选来源，业务 `validate_draft` 提供适用条款、金额上限和业务版本核对。Approval 与 Execution 已增量接入聊天证据、客服决定和客户确认绑定，保留原权限与模拟账本。源码及隔离测试已实现，尚未完成新页面部署和完整业务端到端验收；真实模型决策另验。

## 存储与接口

- `DecisionScope` 由授权服务在当前事务生成。冻结会话、事项、工单、订单、商品、公开输入截至序列、输入摘要、证据图摘要、证据标识、业务/政策版本和当前候选依赖。范围内可有多份不可变快照。每份记录保留来源运行或上一版、结构化备选方案、核验结果、未决事项和期限。
- `DecisionService(resolve, validate)` 的方法接收调用方事务 `Session` 和经认证的 `UserContext`。resolve 首先在同一事务锁会话，返回当前范围和客户归属。validate 再走既有业务规则，核对结构化方案与当前证据。任何内部 Agent 候选写入仅允许受信 worker 接线调用，禁止直接对客户端开放。
- `record_candidate` 写原始候选及每项程序结果。相同运行标识和请求重放原记录。候选草案可保留不合格方案供客服判断，但阻断方案不生成公开 offer。
- `review` 绑定原候选的 ID、版本和摘要。客服可采纳选项、修改为新版本、拒绝、请求证据或接管，须填写理由。采纳和修改重跑程序核验。修改产生新快照并保留原候选。拒绝、补证和接管撤下当前公开 offer。只有通过的选项可发布，未决候选可由客服明确修改并重新提交。
- `respond` 由归属客户对精确 offer 作接受、拒绝或请求修改；接受后可追加撤回或修改，原记录保留，执行依据最新答复。同一幂等键复用原记录，不同负载冲突。原始客户确认仍能审计，当前指针变化后不再授权后续动作。
- `require_accepted_offer` 是 BusinessService 事务接线口，比较当前绑定及依赖、offer、客户确认和结构化动作。新提案保存其返回的精确绑定。审批和执行均重查绑定，沿用业务审批权限、过期、幂等及执行账本。为避免旧入口绕过，新增带聊天绑定的提案必须在 BusinessService 统一路径检查；未纳入聊天的普通工单保持原流程；已纳入聊天的旧无绑定提案不能再审批或执行，但历史读取和已经执行的账本重放保留。客户同意与客服决定均不能替代财务批准。
- 聊天序列用于回看快照。当前有效性比较显式证据依赖和业务版本。无关消息不改变依赖。公开卡片使用白名单投影，包含动作、商品、分/数量和程序认可的政策编号，模型原文、内部证据和客服原因由内部工作台单独显示。

## 验收

隔离测试应验证候选和客服修改均可回读、客户确切绑定、权限与跨客户拒绝、过期/依赖漂移、费用和数量约束委托、程序拒绝、同键不同请求冲突及更新后旧 offer 失效。集成阶段另验真实数据库事务、迁移恢复、浏览器客服和客户路径，以及旧 API 无法绕过新绑定。真实模型候选和独立人审需另存原始证据。

结构化非执行候选包括 `REQUEST_EVIDENCE`、`NOT_SUPPORTED` 和 `HUMAN_HANDOFF`。每项绑定所涉订单行、明确理由、可选替代，补证还必须列出具体缺口。客服可采纳后续处理方式，记录不生成业务 offer。客服修改仅清除明确列出的原未决项；其余问题继续阻断执行型 offer。快照以 `origin=AGENT|SUPPORT_MODIFICATION`、原运行标识、来源账号和父快照区分。评测按原 `AGENT` 快照取输入和候选，客服修改作为独立事件。

内部 worker 使用实际客户发起者或支持人员的授权范围，不冒充客服。接线方在同一事务核对持久运行确实属于当前会话、事项、发起者及冻结输入，并提供预期的上一快照引用。已被客服处理的同依赖候选不能被后到 Agent 覆写。客服提交提供当前处理记录 ID，以拒绝同一候选上的陈旧并发修改。客户方案通过单独读取接口取得当前精确 ID、版本和摘要。
