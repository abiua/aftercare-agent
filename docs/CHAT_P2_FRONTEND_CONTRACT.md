# P2 聊天前端接口与交互

以下是拟议接线和验收边界。当前客户聊天已支持同会话连续发消息、多图附件、刷新回读和客服回复。P1 确定性退款、订单确认和人工接管继续沿用原入口。[P1 接口](CHAT_P1_CONTRACT.md) · [证据与调度](CHAT_EVIDENCE_DECISION_CONTRACT.md)

## 提交和等待

| 信号 | 页面表现 | 调度含义 |
| --- | --- | --- |
| 正在编辑文字或本地选图 | 显示输入内容和待发送照片。客户可分批补图 | `typing` 仅在当前页面使用，无网络写入。编辑或选图不建立分析任务、不推进代次、不延长等待。 |
| 开始发送 | 保留原文和照片顺序，显示“正在发送”。同一请求在回复前防重复点击 | 复用 `POST /conversations/{id}/messages`。原文不裁剪，`trim()` 仅验证是否为空。每次提交一个 `client_message_id` 和有序附件。相同原文与附件重试复用原 ID，修改内容为新请求。 |
| 已暂存但图片未提交 | 页面可显示服务器已收到上传请求，仍在接收照片。只有已提交消息进入历史 | `pending_uploads` 由已授权、已持久暂存且仍有效的附件批次计算。客户端“选了图”或正在上传的进度不能代替服务端暂存。图片批次到期按未收到处理，允许后续成功提交作为新输入。 |
| 服务器提交成功 | 同一条消息显示完整的原文和本次已提交照片，立即允许继续发送 | 只有服务器确认提交后，才把这批文字和图片作为已接收输入。同一事务更新分析代次和持久调度记录。一次提交中的多张图作为同一批，随后另发的图仍可进入同一事项的聚合窗口。 |

P1 暂存发生在 multipart 解析和图片初检之后。网络上仍在传输、尚未进入服务器暂存的照片没有可信的 `pending_uploads` 记录。首版用服务器静默期覆盖这一常见间隔。若后端需要在上传请求解析前登记，可另加有期限、绑定当前事项和消息 ID 的暂存登记，成功提交仍以服务器确认的附件为准。页面不反复续期，也不在空闲时创建虚拟上传。

首轮建议由后端配置三个独立上限。静默期可用 2–3 秒起步，连续输入窗口最多 10 秒，已登记的真实在途上传最多占用 30 秒。这些是初始建议值，前端不写死，也不自行倒计时启动调查。静默期随相关的新提交更新，但从第一条待分析输入起设硬截止。服务器在硬截止前完成已提交照片的聚合，或记录未收到的附件后按已有证据继续。调查前可发“已收到，正在整理”，不因首条文字立即追问照片。图片完成后有新输入时，建立下一代，替换此前未发布的分析。额度和模型时限沿用后端独立约束。

## 读取进度和公开观察

消息仍按 `sequence` 分页、合并和去重。建议在现有 `ChatPage` 和发送响应中新增可选 `analysis` 字段，按当前事项返回最新快照。前端使用同一鉴权刷新路径，进度在空消息页也可更新。旧后端没有 `analysis` 时按 P1 展示，页面不会自行合成处理状态。

| 字段 | 最小约定 |
| --- | --- |
| `issue_id, generation, state_version` | `issue_id` 区分事项，`generation` 标识本轮输入，`state_version` 标识该事项状态快照顺序。页面忽略落后的快照。不能用消息序列或现有 `conversation.revision` 推测分析代次。 |
| `state` | 建议 `COLLECTING / WAITING_UPLOADS / CHECKING_PHOTOS / WAITING_CUSTOMER / HUMAN_HANDOFF / COMPLETE / UNAVAILABLE`。页面显示“正在整理信息”“正在接收照片”“正在查看已收到的照片”等状态，状态以服务器快照为准。 |
| `input_through_seq, pending_uploads, wait_until` | 当前处理的已提交序列上限、服务器登记的在途批数、可选的 UTC 等待截止时间。可用于状态说明，不展示尚未提交图片的数量或内容，也不由客户端决定是否已超时。 |

后端发布时按当前事项、输入代次、对象范围、人工接管和任务租约校验。旧任务可以记录已发生的用量，不能追加客户可见消息。前端收到更高版本后收起过期可操作卡片，保留已经公开的历史消息。切换会话或失去权限时中止旧请求并撤销图片预览对象地址。每张图仍通过当前会话的鉴权图片接口读取。

新增消息卡片只接受明确的公开字段。建议 `photo_observation` 包含 `issue_id, generation, attachment_refs[], summary, certainty`，引用附件必须属于当前授权会话。可展示“照片上疑似有裂纹，暂不能确认原因”“标签号码不清楚”。模型建议的材料类型、角色提示、原始内部日志和运行参数不进入客户消息。若需要客户补充，`evidence_request` 卡片携带 `issue_id, generation, request_id, prompt, alternatives[]`，允许直接回复文字或照片，或选择“暂时无法提供”。后者通过普通消息或由后端定义的幂等动作写入，服务端按缺口标识停止重复催证。材料桥接和人工审核沿用后台角色及证据边界，客户不用选择材料类型、模型或自行启动调查。

## 前端改动与验证

- `CustomerChat.tsx` 当前以发送期间的本地状态控制按钮，成功后清空草稿，失败时保留本次文本和照片。P2 沿用此机制并补服务器状态说明。草稿内存随页面生命周期结束，历史只从服务器回读。[聊天发送与刷新](../frontend/src/CustomerChat.tsx)
- `chat.ts` 增加可选分析快照、公开卡片和快照合并规则。原有 multipart、消息排序和附件上限保持同一契约。前端测试覆盖旧接口缺字段、新旧快照乱序、同 ID 重试、图像授权撤销与客户可见字段。[聊天类型与请求](../frontend/src/chat.ts)
- 用受控浏览器验证先发文字、紧接着分两批发送多图、旧分析晚到、超时后继续、补证无法提供和人工接管。核对整个过程仅当前代次发布、客户可回读原文和批次，且没有要求用户选择材料类型或模型。真实验收需核对服务端调度时间、实际图像传输与观察记录，受控浏览器用于验证交互。
