# 人工复核可用性审计

## 首要缺口

复核者要回答「客户问了什么，当时系统知道什么，助手实际给出了什么处理意见」。当前页面能打开结果、逐项选择和查看历史，但默认视图没有把这三件事放在一起。用户得自己从技术记录里找客户原话、辨认哪次答复对应哪个业务阶段，再理解总评和逐项判断的区别。已有用户反馈「看不懂你说啥」只说明说明方式需要改进，尚无该样本的人工质量结论。[用户反馈](../reports/human-review-usability-feedback.json) · [真实页面只读记录](../reports/browser-review-annotations.json)

| 当前界面或材料 | 对复核者的影响 |
| --- | --- |
| 人工复核包先讲内部工作笔记。样本又同时要求判断事实、引用、处理和总评。 | 开场问「助手有没有把照片检查通过说成退款批准」，容易让人把内部错误直接算到公开处理意见。包中的英文值和编号增加了第一步操作的负担。 |
| 实验详情先显示程序摘要、引用和费用，然后才进入人工复核。客户原话未在复核入口直接显示。 | 样本案例号不能替代原话。缺少客户问题时，复核者无法判断答复是否切题，例如错发客户具体问的是「需要拍哪几张」。 |
| 关键事实卡展示末态快照，并在每个事实项下重复各步的 `output.notes`。 | 「本次报告结束时」的标签已有必要区分，但仍把晚发生的审核和更早的补证要求并排。复核者需要自己推断时间关系，而且相同多段文字反复出现。 |
| 步骤说明使用 `actual.events` 对象枚举序号，引用和事实正文只展示 `output.notes`。 | 序号缺少业务含义，旧报告缺项或对象顺序变化时不宜当成可信时间线。正文也没有完整体现同一输出中的缺失材料、账本、草案和状态。末次 `output=null` 在这组文字中不出现，容易把此前暂停提示读成最终答复。 |
| 表单先要求选总体结论和写依据，逐项证据在后。复核包的独立人工审核格式与应用的单次结果复核格式并存。 | 用户还没读到对照证据便遇到「通过／不通过」，也可能把「现在看不懂」当成需要提交的复核。两个记录体系的用途、保存入口和后续统计影响需要区分。 |

## 证据能证明到哪里

- **客户说过什么。** 复核包保存了原文及出处。所查四个历史样本的客户原文还可与报告中成功创建工单的描述核对。当前结果详情可从有明确脚本步骤身份和成功创建记录的事件提取描述。缺失时写「本次报告未保存客户原话」，避免用意图标签、参考期望或现行用例库替代原话。后续封存应单独保存当次输入及来源，保留客户原话和客服补充的身份差异。[逐案证据](../data/review/development-review.json) · [重放创建工单](../backend/src/aftercare/evaluation/runner.py#L787)
- **助手向应用发布了什么。** 评测保存脚本步骤调用 Agent 服务读回的公开处理意见，其中可包含规则生成的文字与核验后的引文。应用角色页面能展示这份结果，但离线报告不能证明历史客户实际看到它。当前助手工作面板只对非客户角色显示。因此默认称「应用记录的助手处理意见」，有页面或消息交付证据时另列可见对象。记录字段缺失与明确无输出分别写明。角色完成事件的笔记只放在「内部草稿和笔记」下，标明未核验，不作为公开答复或业务授权。[重放读回](../backend/src/aftercare/evaluation/runner.py#L681) · [角色可见范围](../frontend/src/CaseWorkspace.tsx#L37) · [处理意见与内部轨迹](../frontend/src/RunPanel.tsx#L132)
- **答复当时的事实。** `final_business` 在脚本结束后读取，只能证明收尾状态。重放器已在内存中采集运行周期开始前的业务记录，用于引用适用性等程序判定，但当前报告没有原样保存这份逐周期上下文。旧报告中的成功上传、材料审核和当步 `read` 可以按来源展示各自已记录的动作，单个动作不能推出整个时间点的订单、审批或账本状态。恢复链的 `context_binding` 保存周期、定义版本和摘要，摘要本身不能还原历史业务字段。[末态写入](../backend/src/aftercare/evaluation/runner.py#L563) · [周期取证](../backend/src/aftercare/evaluation/runner.py#L681) · [引用判定](../backend/src/aftercare/evaluation/observations.py#L82) · [上下文绑定事件](../backend/src/aftercare/intelligence/service.py#L758)
- **人工判断的范围。** 已有真实浏览器只读记录证明可以打开表单且 11 项默认为「暂不评」。受控用例覆盖保存及版本冲突。两类证据都没有提交真实质量评分。复核包中的开发样本待审记录也仍为待审，与应用单次结果复核和独立数据集金标分别管理。[只读验收](../reports/browser-review-annotations.json) · [复核包来源核对](../reports/human-review-pack-provenance.json)

## 建议实施顺序

1. **先给用户一张可以直接读的对照卡。** 在案例详情上方显示「客户原话」，再提供可切换的业务阶段，例如「第一次申请」「补齐照片后」「客服审核后」。优先依据报告中的有序脚本轨迹、稳定事件标识及运行周期对应阶段。无可靠顺序的旧记录逐条列出并提示顺序无法确认。所选阶段并列显示「当时能核对的记录」「应用记录的处理意见」。文字原句与结构化事实分开，金额显示元，照片用「错发商品实物照片」「包裹标签照片」等具体名字，审批区分照片审核、方案审批与执行回执。若只有末态，在独立的「报告结束时记录」区域显示，阶段内标明「未保留当时记录」。
2. **封存所需的最小证据。** 后端为新报告添加带版本的逐阶段证据，保留有序事件、角色、运行周期、业务时间及来源，保存当次公开输出及其生成状态、客户原话及出处、答复前已实际读取且可绑定的业务事实。评测脚本在运行前采集的事实应明确叫「执行前记录」。只有与该次运行实际使用的上下文可核对时，才标为「助手答复时使用的事实」。至少分开记录材料审核、方案、审批、账本范围、已确认的回执及缺失原因。按原权限脱敏，不保存工具隐藏推理、材料原文件或密钥。不改写旧报告，也不把后续查询拼回历史。来源和版本详情仍可折叠核对。
3. **先读证据，再选择要不要判断。** 只在阅读对照后显示一个明确问题，例如「这次处理意见有没有说退款已获批？」先提供「返回」「我现在不评」，再提供「正确」「不正确」「无法判断」和一行可参考的说明格式。实际表单仍按原接口单独确认总体、依据和可选逐项标签，默认全空。已有标签替换须显式确认。若某类问题或引用没有公开答复，明确给出缺失原因；不把空输出算通过。按需打开内部笔记和程序检查，避免它们先给复核者暗示。开发包改为按同一顺序提供阅读卡和一句话反馈入口，明确口头反馈不会被自动存成评分。旧接口只支持逐结果的统计范围，不从阶段卡自动生成新的逐阶段标签。

### 用已保存样本验证页面

| 样本 | 用户应能读到的对照 |
| --- | --- |
| DEV-HR-01 | 先展示衣服破损、还未拍照的原话。第一次意见要求补证，随后有上传、等待审核、材料审核记录。末次应用意见请客服确认处理方式、商品和金额。将内部笔记「人工审批状态为已批准」放到折叠的内部栏；收尾记录只用于说明收尾时无方案、审批及执行账本。 |
| DEV-HR-02 | 原话问「需要拍哪几张」。公开处理意见的文字和结构化缺项同时展示，复核者能看到具体是错发商品实物照片和包裹标签照片。草稿里对政策原文的描述单独保留。 |
| DEV-HR-03 | 原话只问有无正式处理记录。呈现本次输出中的账本为空以及处理意见原句，单独标示订单累计退款记录。不能由记录为空推出「从未申请」或「银行未到账」。引用和对应业务前提并列，缺少该次前提证据时显示未登记。 |
| DEV-HR-04 | 原话相同但另一次运行。前两次暂停仍可看，末次写「因模型费用上限转人工，本阶段没有保存处理意见」。早期补证提示和内部笔记均不补成末次答复。 |

**可用性验收。** 让一位不熟悉系统的复核者打开 DEV-HR-01。无需展开 JSON，能指出客户原话、哪个动作只是照片审核、末次意见有没有说已批准退款。再用 DEV-HR-04 验证能指出末次没有处理意见，且可离开而不提交。受控样本覆盖缺失事实、不同阶段的状态变化、内部笔记与公开输出冲突及终止前输出。真实页面只读验收独立记录，用户的疑问只记为可用性反馈。此次审计只读仓库与已保存证据，未访问服务、调用模型或填写评分。
