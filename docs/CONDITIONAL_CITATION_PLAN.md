## 现有核验范围

| 层次 | 当前核验 | 仍需判断的事项 |
| --- | --- | --- |
| 版本与范围 | `resolve_policies` 按意图、商品范围、时间、发布状态和优先级选择版本。`scoped_policy_documents` 再检查申请商品是否存在共同条款和兼容参数。 | 版本在本案范围内，条款正文的业务前提仍可能尚未成立。 |
| 召回与原文 | `_find_evidence` 从有效版本检索，并补入资格要求的政策 ID。`_check_response` 要求 ID 与版本存在，模型确实读到过对应工具结果，引用是原文子串。 | 被检索到、被工具读取和原文匹配，都无法判定该引文能否支持特定结论。 |
| 草案 | `_verify` 对具体动作检查必需引用版本，`validate_draft` 在业务快照中验证范围、可行动作、余额或库存、部分退款处置决定及重复事项。 | `policy_ids_by_action` 是动作依据与准入集合。只读退款进度没有拟执行动作，其结论不经过草案验证。 |
| 评测 | `citation_observations` 目前从冻结政策文档核对 ID 与版本。指标将版本适用率和逐条人工引用支持率分开。 | 增加程序可查条件后，人工支持标签和分母继续独立记录。 |

## 两条现行规则的前提

| 条款 | 可程序核对的前提 | 发布边界 |
| --- | --- | --- |
| `POL08@1.0` | 该退款请求已经有一条可以确认属于同一请求的处理记录。空的已授权账本没有可匹配记录。订单下有记录时仍需确认请求归属。 | 同订单、同行、相近金额或描述都不足以单独证明同一退款请求。重复事项拦截可基于更宽的同类型与商品重叠范围保护写入，其拒绝结果也不能充当请求匹配证据。 |
| `POL12@1.0` | 对应的退款执行记录存在，并有可信的超时或结果未知状态。当前业务的 `UNKNOWN` 可支持该执行记录仍待核对。 | `SUBMITTING` 可以表示提交尚在进行；单凭该值无法证明已超时或结果未知。客服的对账接口为安全起见同时处理 `SUBMITTING` 与 `UNKNOWN`，这是操作范围。状态查询不得自动执行对账或暴露原幂等键。 |

历史累计退款金额可独立展示，无法用来建立上述任一前提。退款进度场景可以读取订单范围的退款执行账本。账本查询成功且为空时，结论只覆盖该账本。权限拒绝、超时或读取失败保持原失败语义。

## 最小实现

1. **为精确版本声明可核对条件。** 初版用项目受控的独立条件表，键为政策 ID、版本和现有政策文档摘要。条目包含目标用途与具名条件，例如 `REUSE_EXISTING_REFUND` 依赖 `SAME_REFUND_REQUEST_RECORD`，`RECONCILE_UNKNOWN_REFUND` 依赖 `REFUND_EXECUTION_RESULT_UNRESOLVED`。只登记核对过正文的版本。同一条件可用于其他 ID。判定逻辑按条件名派发，不按政策 ID 分支。不存在条目、版本摘要不匹配或未知条件名时，保留为未判定。独立条件表可先覆盖现行两个条款，避免改动冻结政策、持久版本、向量键或审批快照；在输出审计记录条件表版本，便于按历史版本解释。
2. **仅从授权快照核对事实。** 条件解析在规则及原文校验之后、最终发布之前，读取当轮的业务快照。仅当查到受信任的同一请求绑定时，才能确认 `SAME_REFUND_REQUEST_RECORD`；第一阶段无需扩大业务接口去猜测绑定，空账本标为前提不成立，订单有记录而请求无法匹配标为证据不足。结果未知的条件绑定到明确的退款执行记录，记录用途限定在描述该记录，禁止由其他执行记录外推本次请求。条件结果使用 `MET`、`UNMET`、`UNKNOWN`、`NOT_ASSESSED`，并保留安全原因码。原文匹配、条件状态和人工语义判断各自记录。条件表、账本或状态缺失时，未知不得视为否定事实。
3. **增量调整发布契约。** 既有 `output.policy_ids` 保持用于候选范围及动作契约，`output.citations[{id,version,quote}]` 保持原文记录。新增与引用逐条对应的 `citation_assessments`，至少含 `id`、`version`、`use`、`condition_status`、`reason_code` 和条件表版本。当前按条款用途评估，同一版本多段引文可共享条件结果；以后需要逐句定位时再增加引文指纹。审计允许保留未满足条件的原文，发布界面把它归为查阅背景，并注明条件未成立或证据不足。程序核对前提成立也只标为「前提有记录支持」。结论仍由事实驱动的输出产生，不从政策引文、模型笔记或条件值反推资金状态。所有草案引用、规则校验、人工审批及执行权限保持原有约束。
4. **前端区分候选、原文和条件。** `RunPanel.tsx` 将候选 ID 显示为「候选条款」，将通过版本与原文核对的引文显示为「原文已匹配」。对结构化条件分别标注状态，并在同一视图中将查阅背景与本次结论的依据分开。旧运行、旧报告和未声明条件的引文显示「条件未评估」，不能把字段缺失解释为通过。评测视图保留原始引文和人工复核入口。若后续增加程序条件覆盖率，单列分母与未知项；原有人工支持率继续使用逐条人工标签。

## 回归范围

- 使用纯测试覆盖候选版本有效但条件不成立的场景。空账本、空账本但历史累计非零、同订单有其他请求、无法建立同一请求绑定、受控已知匹配分别有明确结果。验证一条其他 ID 的合成政策可以复用相同条件，另一个未声明版本保持未判定。
- 覆盖 `UNKNOWN`、`SUBMITTING`、成功或失败、缺状态及跨请求记录。针对 `UNKNOWN` 检查结论只涉及指定执行记录；针对 `SUBMITTING` 检查无独立超时证据时不会提示该条款前提已经成立。读取错误保持失败状态。
- 假模型提供精确原文却声称条款已满足。验证原文保留审计，前提结果来自可信快照，最终内容仍只描述查询结果。现有伪造引文、不可见版本、必需草案引用、超额退款、重复事项、审批与执行保护回归继续通过。
- 前端测试候选与原文标签、条件不成立及未知的显示、旧报告无新字段的兼容。评测测试确认版本命中与人工支持率不会被程序条件结果改写。证据采用开发样例与合成反例；正式保留集和人工金标沿用各自的审阅流程。

本次只核对源码与政策原文并形成设计。未更改应用源码、评测参考、正式保留集或人工标签，未调用付费模型。
