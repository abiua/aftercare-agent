## 接入方式

产品的会话调查图（`investigation/graph.py`）新增一条 `kernel` 路径，由配置项 `chat_investigation_kernel_review` 打开，**默认关闭**。打开后，客户聊天触发的调查在运行绑定里记录为 `kernel`，中途恢复的运行保持启动时的路径。

| 内核层 | 产品里对应的部分 | 本阶段是否改动 |
|---|---|---|
| 执行者 | 调查图的强单阶段（带只读工具，产出主张和候选方案） | 未改 |
| 程序护栏 | 发布前的业务规则校验（订单行范围、证据范围、政策版本、金额校验） | 未改 |
| 独立审查 | 新增 `kernel_review` 节点，复用内核的 `ProposalReviewer` | 新增 |
| 按需专家 | 现有事实/政策/核验深度调查路径 | 未改，路由沿用 |

链路：分流 → 程序可直接处理的案子不调用模型 → 普通案走强单阶段 → 程序校验（先不发布）→ 独立审查 → 放行则发布；要求修改则带着建议重跑一次强单阶段，再过程序校验后发布 → 生成候选决策快照 → 客服审核、客户确认、审批、模拟执行（均未改）。复杂案按现有分流和升级条件进入深度调查路径，不经过新增的审查节点（该路径自带核验角色）。

`investigation/kernel_adapter.py` 是产品侧适配：

- **模型端口**：通过产品现有的模型运行器调用，计入同一次运行的调用次数和费用上限，写入同一套审计记录。审查固定走决策级模型，不降到经济模型。
- **审查输入**：客户陈述，加上调查者实际读取或引用的业务记录和政策条款。不含调查者的提示词、主张和推理。未读取的记录只给出编号清单。
- **提交后端**：审查对象是“将要发布的结论”，不执行任何操作。可执行方案（退款、换发）按提交审查处理，交人工、不支持、要求补材料按放弃审查处理。
- **审查指令**：产品用中文指令，输出格式和原则与评测用的英文指令一致，措辞换成本产品的操作。评测用指令未改，哈希不变。
- **失败处理**：审查输出无效、引用对不上原文、超时或预算不足时默认放行并记录原因；修改阶段失败时保留第一次已校验的结论。

审查结论保存在运行输出的 `kernel` 字段和 `kernel_review` 审计事件里；候选快照的 `route_version` 记为 `kernel`。审查要求修改而最终仍未形成可执行方案时，审查建议会追加到快照的“未解决事项”里，客服审核时能看到。

## 与计划不同的地方

- **没有新增图版本标识。** 现有代码有二十多处按 `chat-investigation-v1` 判断快照、预算和事件，新增标识需要全部改动。改为用路径名 `kernel` 加输出里的 `aftercare-kernel-v1` 区分。每次运行有独立检查点，旧运行不会进入新节点。
- **候选快照结构未改。** 审查全文不在快照里，而在快照所引用的运行记录里。
- **产品里没有直接使用内核的单步引擎**（`ExecutionKernel.step`）。产品的调查阶段有自己的工具循环、预算和审计，替换它风险大、收益小。共用的是契约、审查机制和校验逻辑。评测适配器和产品适配器因此不是同一条执行代码路径，这一点在报告评测数字时需要写明。
- **客户对话层没有接入“转人工前先告知并询问”的审查。** 产品里调查的产物是给客服的候选方案，不是直接对客户的回复；客户回复由现有会话分析和客服环节负责。
- **产品侧专家读端口没有接。** 深度调查路径已有自己的只读工具，没有再把内核专家模块接进产品。
