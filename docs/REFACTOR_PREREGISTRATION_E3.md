# 训练集确认实验 E3（离线预注册草稿）

本文件于 2026-11-15 准备。当前只完成代码、离线测试、清单和干运行，不授权真实评测或模型调用。源码提交哈希在清单中留空，由提交后填写；本次不提交、不推送。

## 要回答的问题

在共同的规则检查下，为低价执行者增加专家和独立审查，能否提高成功题数？与强模型单执行者相比，能否在成功题数相近的情况下减少每成功一题的总费用？前者是主判定 H_lift，后者是次判定 H_cost。描述性统计不参与这两条判定。

## 题目和排程

题目来自固定官方 τ²-bench Retail 的 train 划分，官方源码版本为 `da0835f6c67baef58bdda18f2a3b037dfb3a1754`。train 共 74 题；去掉 `kernel_v3_dev_tasks.json` 的 `development_task_ids`：16、22、29、41、44、54、96，剩余 67 题。

程序读取当前官方数据和开发题清单，核对 `tasks.json`、`split_tasks.json` 的 SHA256。还会检查 train 有 74 个不同题号、排除项恰为上述 7 题且都在 train 中、剩余恰为 67 题且没有开发题。官方数据本身继续受现有 revision 和数据来源哈希校验约束。任何不符都退出；confirm 不接受 `--task-ids`。

固定题号按数值升序排列：

```text
0, 1, 2, 3, 4, 6, 7, 8, 10, 11, 13, 14, 15, 19, 20, 21, 23,
24, 25, 28, 30, 31, 34, 35, 37, 43, 46, 47, 48, 50, 52, 57,
58, 59, 63, 66, 67, 69, 72, 73, 75, 76, 78, 80, 81, 82, 83,
84, 85, 87, 88, 89, 91, 92, 93, 95, 98, 99, 103, 104, 105,
106, 107, 109, 110, 112, 113
```

三组固定为 `S1c,M2,S1`，每题每组一次，共 201 次。沿用 `new_campaign` 的轮转写法：第 i 题从组序号 `i % 3` 开始轮转；三组使用相同的 `42+i` 种子，i 从 0 开始。因此前三题顺序分别为 S1c/M2/S1、M2/S1/S1c、S1/S1c/M2。种子范围 42–108；并发完成顺序不保证与提交顺序相同。种子控制官方编排器，Responses API 不提供供应商随机种子。

## 三组及模型

以下内容来自当前 `aftercare.agent_kernel.contracts.architectures()` 的实际返回值，内核版本为 `aftercare-kernel-v3.1`。冻结清单保存三组完整配置。

| 组 | 执行者及 reasoning | 规则检查 | 独立审查 | 专家 |
| --- | --- | --- | --- | --- |
| S1c | deepseek-flash / disabled | 开启 | 关闭 | 关闭 |
| M2 | deepseek-flash / disabled | 开启 | gpt-6.1-sol / low | gpt-6.1-sol / low |
| S1 | gpt-6.1-sol / low | 开启 | 关闭 | 关闭 |

S1c、S1 的配置对象也保存 reviewer/expert 为 gpt-6.1-sol / low，但相应功能关闭，不据此发起调用。官方模拟客户为 `gpt-6.1-terra` / low，官方自然语言裁判为 `gpt-5.4-mini-2026-03-17`；它与 M2 的独立审查者是不同角色。

配置对象中的 `max_agent_calls` 原值为 48，本次不改模型配置。核对当前实现后，该字段没有用于执行调用上限；实际调用额度由官方适配器外层的 `RowTransport` 按本实验统一的 160 次限制。执行者、专家和审查者共享这 160 次，专家不是额外额度。

## 统一上限

| 项目 | 固定值 |

| 原始运行及补跑合计费用 | $20 |

| 每题每组模拟客户调用 | 60 |
| 每题每组官方裁判调用 | 1 |
| 总调用 | 201 × (160+60+1) = 44,421 |
| 每次最大输出 token | 1,500 |
| 并发 | 6 |
| 每次运行超时 | 900 秒 |
| 每次请求超时 | 120 秒 |
| 官方编排最大步数 | 沿用现有 100 |

三组使用完全相同的上限。confirm 会拒绝与上述参数不符的启动参数。费用控制沿用预留再结算机制，未结算调用保留预留额；临时预留也可能使后续调用被阻止，即使最终已结算费用还没有达到 $20。

## 固定判定规则

成功指官方 `official_reward == 1`，不自行改分。每组分母始终是 67；缺失、未完成、无得分、预算耗尽项保留在分母里，没有成功分数就不计成功。

- **H_lift**：M2 成功题数严格大于 S1c，且按逐题成功/未成功配对的 McNemar 精确检验双侧 p < 0.05。复用 `analyze_kernel_campaign.mcnemar`，包括该函数保留四位小数的输出约定。
- **H_cost**：M2 成功题数至少为 S1 成功题数减 3，且 M2 每成功一题的总费用严格小于 S1。总费用包含执行者、专家、审查者、模拟客户、官方裁判和失败尝试，补跑也累加。三组中任一组有未结算调用或费用不完整时，H_cost 为 `undetermined`；M2 或 S1 零成功时，每成功费用未定义，也记 `undetermined`。不把未知费用当零。
- 两条都为 false，结论为 `no_advantage_shown`。如果一条或两条为 true，分别报告成立的判定；没有 true 但 H_cost 未确定时，结论保留 `undetermined`，不写成“两条都不成立”。

描述性统计包括每组成功数、Wilson 95% 区间、每题费用，以及现有 `arm_report` 中的错误写入、放弃、未完成、角色调用、费用、耗时、审查和专家字段。每题费用同时提供总费用/67 的组均值和逐题费用。

M2 另报：专家咨询次数（仅实际 consultation 事件）、成功执行的专家读取次数（read_log 的 executed 项）、专家缓存的自写入更新事件数（每个 `expert_self_write_rebased` 事件计一次）、金额规则触发数（guard/post_review_guard 中的 amount_arithmetic，不重复计 soft-unresolved 说明）、审查 revise 数、带 fallback_reason 的审查数、IncompleteResponse 调用数。最后一项按账本 call_id 去重，独立尝试分别累计；传输层补记已结算的不完整响应异常，不改变调用、收费或重试方式。缺失轨迹会列出，已记录事件的计数不等于证实缺失部分为零。上述信息均不参与主、次判定。

## 执行和补跑

每题每组只跑一次，不挑选较好结果，不因已有失败分数而重跑。只有 `status` 为 `error` 或 `unknown` 且没有官方得分的条目，才允许沿用 repair 在同级 `run-v1.repair` 目录独立补跑一次。已有 0 分、timeout、budget_exhausted 均不符合条件。原始记录必须全部结束且文件齐全；补跑目录已存在或来源本身是补跑时拒绝。

本次对 repair 的最小修改是支持 `scope=confirm, split=train`，并核对完整的 E3 题号、排除项、三组、种子、内核和额度。其他 test 补跑行为保留。补跑继续校验原始记录哈希、清单哈希、适配器及内核哈希；用原题号、组别和种子载入 train 题目。

补跑额度不得超过原 $20 扣除已结算费用和未结算预留后的余额，同时沿用现有单次补跑最高 $3 限制。补跑调用数也不超过原 44,421 次的剩余量。账本缺失、不完整或费用上界失效时，拒绝补跑。

分析脚本自动检查同级 `.repair` 目录并调用现有 `merge_repair`：使用补跑记录作为该项结果，保留来源核验与原始失败信息，原始与补跑的调用、费用、耗时和事件全部计入。即使补跑仍失败，也不恢复为挑选过的结果。每组分母仍是 67。

离线分析入口为 `scripts/analyze_kernel_e3.py --directory ...`，默认目录 `.runtime/kernel-e3/run-v1`，默认结果路径 `evidence/architecture_refactor/kernel_e3_results.json`。E3 未运行时不生成假结果；测试假数据及测试结果仅存在临时目录。E2 的 hypotheses 和结果文件不变。

## 费用估算及局限

按现有账本逐调用读取总费用，包含模拟客户和裁判。这里仅作计划估算，不调整判定规则，也不作为 E3 结果。

| 来源 | 次数 | 已结算总费用 | 每题费用 |
| --- | ---: | ---: | ---: |
| E2 / S1c | 40 | $0.506562 | $0.012664 |
| E2 / S1 | 40 | $5.141925；另有 2 笔未结算、预留 $0.047640 | 已知 $0.128548；计入未结算预留为 $0.129739 |
| v3 开发 run-v1 / M2 | 6 | $0.482738 | $0.080456 |
| v3.1 开发 run-v3.1-fixcheck / M2 | 3 | $0.309833 | $0.103278 |

两个 M2 开发批次合计 9 次尝试的加权均值是 $0.088063/次；其中复查题与前一批次重合，不是 9 道独立题。按两批均值分别外推，E3 201 次约 $14.85–14.93 或 $16.38–16.46；按 9 次尝试合并均值外推约 $15.36–15.44。每个区间左侧只含 S1 已结算费用，右侧再计入未结算预留，不是统计置信区间。

$20 高于这些点估算，但仍可能在跑完前触发。按 v3.1 三题均值外推、并计入 S1 预留的 $16.46，余量只有约 $3.54（约 21.5%）。题目组成、长对话、并发预留、模型波动和技术补跑都可能消耗余量；更高的每题调用上限也使旧费用不能保证新批次完成。

实验检验力有限，通常约需 M2 比 S1c 多对 8–10 题才可能显著，具体仍取决于两组不一致题目的双向分布；这不是替代 McNemar 检验的固定门槛。每题每组只运行一次，不能估计同题重复运行波动。v3.1 仅经过 3 题真实复查，不能据此保证其在全部 67 题上的质量。官方 test 的 40 题已经用于失败分析，不再用于确认；E3 是剩余 train 题上的确认，不能当成独立官方 test 成绩。
