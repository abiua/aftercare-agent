# 售后 Agent 开发样本人工复核包

四次真实模型运行覆盖三种意图，其中一次是同一货损案例的预算失败。订单、材料和政策来自模拟业务快照。独立人工复核全部为 `PENDING`，正式留出集未参与本包。[逐案证据与待填字段](../data/review/development-review.json)

## 先看一个容易理解的例子

这是一笔模拟售后：客户说衣服坏了，后来补交了照片。系统里的真实记录是：**客服确认照片已通过检查，但还没有提交退款方案，也没有人批准退款，更没有退款记录。**

助手的一段内部工作笔记却写：「人工审批状态为已批准」。这句话可能让人以为退款已经获批。你要核对的是：助手有没有把“照片检查通过”说成“退款批准了”？

这段内部笔记与最终展示给客服的答复分开看。最终答复是「已核验业务条件，请客服确认具体处理方式、商品和金额」，没有直接说已经退款。某一句有问题，不自动代表最终答复、所有引用或整个系统都不合格。

可以只回复哪句话看不懂，或者指出哪句话不符合记录；不必理解程序编号，也不用一次给整案打分。目前该案仍待审核，没有将“看不懂”记为正确或错误。

## 一页审核说明

每次取一个 `review_id`。先看原句、模拟订单事实和条款原文，再看角色输出与应用实际发布内容。最后对照程序检查。材料审核记录属于脚本执行业务步骤，评测人工意见须由复核者另填。

| 判断 | 复核时核对 |
| --- | --- |
| 事实 `facts` | 商品、签收、材料状态、金额、是否存在账本或审批，能否从当时系统记录推出。客户陈述、业务字段与外部实际情况分别判断。 |
| 引用 `citations` | 对照 ID、版本和原文，看所引条款是否支持这次结论、前提是否成立。没有引用时，判断该回答是否仍需要依据。 |
| 处理 `handling` | 回答是否解决用户这一问，需补证时有没有说清楚，是否区分可申请、已审批和已执行。遇到失败时，检查是否交代状态与下一步。 |

三项分别填 `PASS`、`FAIL`、`UNSURE` 或 `NA`。只有该项确实不适用时填 `NA`，并写原因。在 `overall` 填总体判断，`rationale` 写一句依据，尽量指向条款、事实字段或角色事件编号。提交时记录 `reviewer` 和 `reviewed_at`。程序判定不能替代人工意见。简短回复可直接使用下列格式。

```text
DEV-HR-01｜事实 PENDING｜引用 PENDING｜处理 PENDING｜总评 PENDING｜理由 PENDING
DEV-HR-02｜事实 PENDING｜引用 PENDING｜处理 PENDING｜总评 PENDING｜理由 PENDING
DEV-HR-03｜事实 PENDING｜引用 PENDING｜处理 PENDING｜总评 PENDING｜理由 PENDING
DEV-HR-04｜事实 PENDING｜引用 PENDING｜处理 PENDING｜总评 PENDING｜理由 PENDING
```

## 待审样本

### DEV-HR-01 · 货损，补证后恢复

> 拆到第三层泡沫才看到防晒外套断了一截，第一次找你们，还没来得及拍照。

订单已签收、支付已确认，订单实付 67,683 分，申请行 L01 可退上限 35,900 分。首次缺商品和外包裹照片，随后两张材料上传，模拟材料审核通过。账本、正式方案与财务审批均为空。应用最终发布「已核验业务条件，请客服确认具体处理方式、商品和金额。」动作为空，引用 `POL06`、`POL14`、`POL09`、`POL02`，条款和引用原文见 JSON。程序检查 10 项通过，结果仍待人工复核。

重点看协调角色曾写「人工审批状态为已批准」，与校验角色区分材料审核和财务审批的表述是否一致。核对发布内容是否还需要说明退款上限及其含义。[原报告](../reports/compact-multi-recheck.json)

### DEV-HR-02 · 错发，等待照片

> 单上写降噪耳机，我拆出来的是另一个牌子。需要拍哪几张？

订单已签收，L01 为降噪耳机，实付 89,900 分。暂无材料，规则列出缺项 `WRONG_ITEM`、`LABEL`，`POL13@1.0` 原文要求实物照和包裹标签照。模型角色草案明确提到两类照片，但称未读取到具体拍摄要求的政策原文。应用发布「请补齐所列材料后继续。」并列出两项缺失材料，无引用原文或处置动作。程序检查 4 项通过，结果仍待人工复核。

重点看草案和发布内容分别能否回答“拍哪几张”，以及是否应直接说明标签指包裹标签。[原报告](../reports/comparison-single-analysis.json)

### DEV-HR-03 · 退款进度，账本为空

> 上周问过能否退款，今天只想查有没有正式处理记录。

订单退款执行账本为空，历史已退款为 0 分。校验角色区分了“系统未找到执行记录”和“从未申请或外部未到账”，并指出 `POL08` 和 `POL12` 的前提现有记录尚无支持。应用最终发布「退款进度仅根据当前模拟账本反馈。」，结构化账本为空，引用 `POL08`、`POL12`、`POL01`，无处置动作。程序检查 5 项通过，结果仍待人工复核。

重点看引用的前提与本案事实是否匹配，以及发布结果对用户是否足够明确。[原报告](../reports/live-recheck.json)

### DEV-HR-04 · 同一货损开发案例，预算失败

使用 DEV-HR-01 同一输入的另一次独立运行。保留前两次暂停和已完成角色的模型派生笔记。最终步骤因 `MODEL_COST_BUDGET_EXHAUSTED` 进入 `NEEDS_REVIEW`，最终 `output` 为 null。程序 8 项通过、2 项失败，总结果 `FAILED`。没有最终答复或正式方案可供评分。

重点看失败状态和接管线索能否支持后续人工处理。如引用或最终答复无法评定，按缺失证据记录。[原报告](../reports/post-upgrade-c001-multi-routed.json)

JSON 内每案包含报告摘要、实验 ID、结果 ID、业务案件 ID、运行 ID 和线程 ID。角色笔记取自模型角色完成事件。应用发布内容单独保留，它可包含规则生成的话术与已校验的模型引用。程序检查的期望值来自原开发脚本，人工栏均待填写。

## 已收到的逐句反馈

用户针对DEV-HR-03历史应用回复“退款进度仅根据当前模拟账本反馈。”明确反馈：“没说清楚，应直接说明没查到记录”。仅记录该句清晰度不合格，见[原话与范围](../reports/human-review-dev-hr03-clarity.json)。事实、引用、总体处理、独立金标与发布批准仍PENDING；未写入整案PASS/FAIL，也不将反馈套用于修复后的新运行。

用户针对 DEV-HR-01 历史协调角色内部笔记“人工审批状态为已批准”反馈：“不准确，容易误以为退款已获批”。已核对原报告摘要和角色事件，记录为该句审批对象表述不准确；不延伸为公开答复、整案事实/引用/处理评分或发布意见。[原话与范围](../reports/human-review-dev-hr01-approval-wording.json)。原逐案人工栏仍 PENDING。现有代码已区分材料审核与未查询的财务审批，这不代表修复后的新模型输出已经通过人审。
