# 审查链路 v2：实施与离线验收

2026-11-14。本次按操作依赖 → 修改落实 → 审查失效处理实施。只使用本地测试和已保存轨迹，新增付费模型调用0。旧E2评分、原始轨迹、计费账本和冻结清单不修改；v2结果不得混入v1的E2统计。

## 实现内容

- `dependencies.py`集中维护规则来源、操作影响和冲突检查。改商品后不得再改地址等属于政策限制，不伪称官方工具全部会拒绝；改付款后付款记录变化使再次改付款受限。取消只限制订单写操作，不禁止查询。
- 护栏在允许的订单写入中附带操作影响。S1/S1c不新增审查或依赖清单否决，S2/M1/M2共用新审查逻辑。工作区原有的用户名认证修复保留，不能把它算作本次审查改动。
- 请求清单有订单、操作、商品范围、状态、客户原话和处理结果引用。状态区分待处理、已完成、无法办理、撤回、同意延期/转人工。撤回和延期需要客户原话，完成需要对应工具成功记录；引用核对证明来源存在，不证明语义已被独立验证。
- 当前动作可以完成的那项请求不拦自己；同类型但其他商品的未完成请求仍会检查。模型写allow也不能覆盖清单中的操作依赖冲突。清单逐条校验，不合格条目丢弃并记录，不影响其余条目。只有找不到当前写入对应的有效条目时，清单才使审查无效；依赖冲突只检查pending，unavailable不拦。
- 要求修改后最多生成两次。仍转人工/拒绝、或相同写入相同参数，会再次提示。每次均检查硬规则和新动作的依赖；改变无关参数不能绕过依赖。两次后纯模型意见未落实可放行但明确记录，只有order_dependency_conflict会因审查链路的依赖判定阻止执行；原有业务硬规则保持不变。输出改变仅记为“动作改变、语义未验证”，不声称问题一定解决。
- 最近两次审查意见带提议、证据摘要和落实结果进入下次审查；不带执行者内部上下文。对话前缀改变时清空历史，历史意见仍明确为待重新核实的意见。
- 审查容忍JSON代码围栏和多余字段；逐条丢弃无效引用，修改意见无有效引用则无效。记录失败阶段、类型和前300字符；最多重试一次，预算耗尽不重试。
- 审查仍不可用时：无订单依赖影响的操作可记录后放行；有依赖影响的写入带程序提供的操作后果，让执行者重新生成一次，通过原有业务硬规则后接受结果，记录review_unavailable；不因清单缺失或审查失效抛GuardRejected。只有仍能从有效条目确定order_dependency_conflict时才硬拦。预算耗尽不额外调用执行者，保留已通过原有护栏的原提议并记录跳过生成原因；已知依赖冲突仍拦截。
- 官方适配器即使在护栏或预算异常退出，也保存最后一步审查和处理轨迹。产品模型适配器为失败重试使用独立调用编号、保留重试提示与失败详情及丢弃条目。
- 内核版本升为`aftercare-kernel-v2`。产品调查图仍生成供人工审核的候选，不把官方零售订单工具的锁单表冒套到退款候选；完整的两次修改执行路径在官方内核中实现，产品调查图不因此自动变成相同执行流程。

## 免费验证

本次单元测试覆盖：操作依赖、当前请求不自我拦截、其他商品不漏检、撤回/延期证据、伪造完成条目丢弃、当前条目缺失、引用容错、两次修改上限、修改无关参数、审查失败后备、预算耗尽零重试、历史隔离。

`scripts/replay_review_v2.py`没有网络或模型客户端：

- 第97题：人工按原始客户消息标注“改商品待处理＋改地址待处理”，即使审查模拟输出allow，程序仍拦住先改商品；这是程序规则验收，不是模型提取能力验收。
- 第27题：使用原记录中第二次审查意见和仍转人工的修改动作，确认会触发第二次生成；第二次澄清回复是显式测试替身，不冒称真实模型已经改正。
- 五组40题，共200条最终轨迹逐条扫描、登记文件哈希、受影响写操作以及后续同订单操作。S2/M1/M2分别有27/25/25条原成功轨迹需要新的请求清单，均登记为待标注核对；不把缺失旧清单导致的保守拦截计作模型误拦率。S1/S1c不新增该项门禁。

机器记录：[200条回放登记](../evidence/architecture_refactor/review_v2_replay.json)。该登记覆盖全部轨迹，但不是77条成功路径已经完成语义标注、无误拦的证明。

## 边界与后续

程序只能基于模型提取且有来源的清单检查依赖，仍可能遗漏请求或误读“同意延期”。不能把整个判断称为完全确定。两次修改也只检查可确定的动作变化和依赖，不保证所有自然语言意见都已落实。

尚未进行真实模型小测、浏览器验收或新E2批次；不能据此宣称成功率、费用或误拦率改善。本次没有更改专家查询/缓存，也没有实现金额算术校验，它们属于前次复盘的其他改进项。

额外调用按分支计：每步初始执行最多2次（含原有硬规则纠正），审查最多2次，修改最多2次（审查失效后最多1次）；均服从已有总调用/费用限制，预算耗尽不得借后备路径继续调用。不能用旧版6～8次修改推算新版真实费用。

## 本次放宽（用户明确要求）

1. 逐条保留有效请求，丢弃记录含审查尝试编号、条目索引和原因；其余有效pending冲突不会因存在坏条目而被清空。
2. 审查不可用不再构成硬否决，锁单提示直接进入一次执行者重新生成输入，结果以review_unavailable登记。此路径不代表审查已经通过。
3. unavailable、completed、withdrawn、deferred均不参加pending依赖冲突检查。

保持未提交；不修改.runtime原始文件，不调用真实模型。评测指标和真实模型效果保持未验证。

## 真实模型小测（审查单步，2026-11-14）

脚本 `scripts/run_review_v2_minitest.py`，独立审查 gpt-6.1-sol，只调审查、不调执行者。样本为E2中M1官方成功轨迹的全部33个锁单写入步骤，加第97题M2先改商品一步。34个样本全部完成，39次调用全部结算，费用$0.705102（上限$1.5）。原始结果在 `.runtime/review-v2-minitest/run-v1/`，汇总在 `evidence/architecture_refactor/review_v2_minitest.json`。

| 指标 | 结果 |
|---|---|
| 成功路径被程序判为锁单冲突 | 0/33（Wilson 95%上界10.4%） |
| 第97题被拦下 | 是，审查自行列出“改地址未完成” |
| 清单含当前写入 | 32/34 |
| 重试后仍无效、走后备 | 2（101、102题同一步） |
| 用到重试 | 5 |
| 模型自身要求修改 | 1（53题：客户的退款时效问题未回答） |

两次后备的原因相同：审查把替换后的新商品号也写进了 `item_ids`，与“只列订单中被改的原商品”不符，匹配不上当前写入。实际运行中它们不会被拦，但会多一次执行者重生成。

已修复（小测之后，未改审查指令）：`dependencies.fulfills` 匹配商品类请求前，先去掉出现在当前调用 `new_item_ids` 中的商品号；操作名、订单号仍须一致，无关商品号仍不匹配。用小测保存的真实输出离线复核：101、102 两题的清单现在能匹配当前写入且不判冲突，97题仍判冲突。上表数字是修复前的原始结果，不改写。

只测了单步审查，没测执行者收到反馈后的行为；样本全部来自M1成功轨迹，不能外推为整题成功率。
