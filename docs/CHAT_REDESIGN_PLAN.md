# 聊天售后增量改造：差异、计划与验收

2026-11-11。依据用户本日十二项调整方案；这是待实施设计，不是完成报告。现状按本地源码核对，旧评测结果保留原范围。新目标优先于旧计划中的固定三角色和五分钟硬门槛。不重建项目、不删除既有数据、不接真实支付。

## 1. 定位及现状差异

客户通过聊天办理售后，Agent 调查并提出候选决策，客服审核决策。客户不选择内部分类、模型或运行模式，也不启动/恢复 Agent。后台保留现有表单及审批/测试工具。

| 要求 | 已有能力（源码依据） | 需要新建或修改 | 尚未验证 |
|---|---|---|---|
| 连续多模态会话 | `intake.py:IntakeService.preview/confirm` 单文本预判、本人订单确认；`CustomerIntake.tsx` | 持久会话、不可变消息、多图附件、客户聊天页、公开回复投影 | 连发、刷新、补图后同会话自动推进 |
| 关联工单 | `business/models.py:Case` 客户/订单/商品范围，范围唯一约束；`service.py:create_case` | 会话内事项与工单关联；明确另一订单/新事项后新关联；普通补充不得建单 | 并发绑定、跨订单图片隔离、已关闭事项新请求 |
| 图片理解 | `ObjectUpload/Material/MaterialReview` 私有对象、摘要、人工材料审核；上传接口一图且必须已有工单 | 建单前会话附件、多图提交、真实视觉输入、类型建议与观察单独存储 | 模型确实接收像素、模糊/冲突/注入图、真实性边界 |
| 证据分层 | 工单事实、材料审核、版本绑定和原始对象 | 客户陈述/模型观察/已核实记录三个来源，原始引用、对象范围、支持/反驳/不足、失效依赖 | 不把模型判断提升为业务事实 |
| 自动分流 | `graph.py:_gate` 缺项与定向退款可走程序；调用方指定single/multi | 复杂度与风险独立；规则先行，歧义才轻量模型；单Agent升级及人工接管 | 普通/复杂分别路由质量，金额不会强制多Agent |
| 三角色协作 | `build_graph` coordinator→policy→verifier串行；有限工具调用与一次整轮返工 | fact investigator/policy analyst首轮独立并行；反例核验；结构化交接与局部补查 | 独立取证、并行预算预留、局部失效、未知请求恢复 |
| 完整候选决策 | `Recommendation`动作/行金额/引用/冲突，业务草案校验；`RunPanel`带入方案 | 支持补证/暂不支持/转人工，金额依据、不确定项、备选、冻结输入与程序检查 | 客服介入前不可覆盖的完整快照 |
| HITL及客户确认 | support提案→独立approver批准→support执行；幂等账本 | 客服采纳/修改/拒绝/补证及理由、客户方案确认各自独立记录 | 旧执行接口也校验聊天工作流门槛；过期确认不能执行 |
| 决策评测 | `evaluation` 数据集/运行/版本/人审/调用成本及正式冻结工具 | 原始Agent决策和人工修改分离；独立盲审、多合理方案、新增信息分层 | 新指标与真实图像端到端、三基线与消融 |
| 展示与演示 | 客服/审批/测试工作台，SSE及内部trace；客户材料页 | 客户统一回复与卡片；后台证据、冲突和补查变化视图 | 一个普通案+一个独立取证纠错复杂案，时间仅参考 |

目前 `_run_role` 最多两次模型步骤、工具同一批顺序处理，不能称“强单 Agent 自主多步并行工具基线”。模型消息当前只有文字JSON和材料元信息，不能称自动看图。现有 AgentRun.output/事件不等于完整的冻结决策及独立人工判断协议。

## 2. 模块与数据结构

### 复用并保持兼容

- `business/service.py`、模型及规则：订单归属、商品范围、可退额度、政策生效时间、库存、独立审批、执行账本及未知结果核对继续作为唯一业务约束。
- `intelligence/service.py/tables.py`、`dispatch.py`、队列与Worker：复用授权、租约、调用审计、预算、恢复机制。旧graph版本/检查点继续读；新流程显式版本化，禁止用新节点直接恢复旧检查点。
- `evaluation/*`、备份恢复、旧报告/数据集只新增版本，不改写历史结果或提升历史证据等级。
- `frontend`客服表单保留；客户聊天为主入口，旧表单作后台/兼容入口，不向客户暴露内部运行参数。

### 拟新增结构（由迁移新增；字段在各阶段契约中冻结）

| 结构 | 核心字段与约束 |
|---|---|
| Conversation | owner/customer、状态、消息revision、公开序列、创建时间；用户仅可读写本人；人工接管状态 |
| ConversationMessage | conversation、seq、role、text、client_message_id、内容摘要、created_at；同会话客户端ID唯一，原文不可变；修正用新消息引用旧消息 |
| ConversationAttachment | conversation/message、私有对象key、SHA、MIME/大小、原文件名；不要求客户选择材料类型；上传暂存与提交有所有权校验及孤儿清理 |
| ConversationCaseLink | conversation、事项ID、case/order/line范围、状态、确认依据message；一个会话可有明确区分的事项；附件先属消息，跨事项引用需明确绑定 |
| ConversationTurn/Job | 输入消息截至序列、revision、附件集合、状态、deadline、lease、published_revision；同输入去重；新消息使旧分析不可发布 |
| EvidenceObservation/Claim | source_kind(customer/model/business/human)、原始消息/附件/业务引用、order/line/version范围、观察、模型及提示版本、支持状态、依赖与失效原因 |
| InvestigationTask/RoleResult | 角色、目的、允许工具、输入版本、证据引用、未决问题、补查建议、调用预算、轮次/期限；首轮互不暴露未经核实结论 |
| DecisionSnapshot | 不可变输入清单/图摘要/业务政策版本、候选动作/对象/金额数量/依据/备选/问题、程序检查、run/角色证据引用、发布状态 |
| SupportDecision | 原decision、采纳/修改/拒绝/补证/接管、修订内容、理由、新增信息、操作者及时间；不覆盖原Agent输出 |
| CustomerDecision | 客户可见offer的ID/version/hash、同意/拒绝/修改诉求；与SupportDecision、Approval、Execution分别记录 |
| DecisionReview | 独立判断提交时间与建议暴露时间、可接受方案集、逐项判定、证据/新增信息；不以客服动作天然当金标 |

会话版本独立于case/materials/facts版本。消息提交和队列派发使用同事务outbox；消息可能不改变业务事实，不能无故使财务审批失效。真正改变对象/金额/证据的输入会使依赖决策过期。客服审核/客户同意/财务审批各自绑定确切决策或方案版本，最终执行在BusinessService事务内检查，防止旧API绕过。

暂存图片不得为了调用旧接口伪造材料类型；P1保存为会话附件，P2由模型建议类型、必要时澄清/人工核实后建立材料关联。原图和历史审核不覆盖。对象存储与数据库不宣称分布式原子：采用上传意图、状态及可重试清理，关联成功后再公开消息。

## 3. 分阶段路径与验收

每阶段交付可体验路径，范围以该阶段声明为准；未接入模型的路径标明程序回复，未具备的能力不做演示伪装。

### P1 会话及客户入口

路径：客户发问题→必要时本人订单卡片→同会话补充文字/多图→关联现有或新工单→后台读消息并公开回复→客户刷新仍能继续。明确退款记录问题可直接查询并返回有记录支持的结果。

改动：新增conversation后端/API/迁移，复用私有对象存储与订单权限；新增CustomerChat和统一消息卡片；后台增加同会话查看/回复；保留旧表单。客户API不接受mode/model/material_kind等内部控制。

验收：文字单发、文字+两图、图先于订单确认、连发补充；网络重试仅一条消息/一次关联；刷新恢复；跨客户读取/附件拒绝；普通补图不重复建单；另一订单先确认再另建事项且不混图；公开回复不泄露内部trace；老工单/旧报告仍可读。退款查询走真实API/数据库，模型调用为0。P1不宣称图片理解或Agent自动决策完成。

### P2 图片理解与自动补证

路径：客户说货损后连续发图→消息汇集→实际视觉模型观察→分类/缺口在原聊天回复→补图自动继续；无法补证转替代证据/人工。

改动：视觉能力声明及实际传输适配、图大小/解码/数量限制、观察记录与来源分层；持久debounce/附件上传中状态、自动调度、revision发布栅栏；每个缺口有限追问。

验收：实际图片输入的正常/模糊/标签/疑似裂纹/矛盾/含指令图片；核对送出的图摘要与原图及模型结果，不用mock证明视觉；连续文本+图片不在图片提交前抢先催图；旧调用晚到不覆盖新输入；用户说无法提供则停止相同追问。并发/重启后无丢图或重复回复。观察“疑似”不能变成运输归责或已核实事实。

### P3 候选决策与HITL

路径：常规工单由Agent形成完整决策卡→客服采纳或修改并写原因→客户确认必要事项→独立审批→模拟执行→会话通知实际回执。

改动：不可变DecisionSnapshot、SupportDecision/CustomerDecision、后台卡片、会话公开方案/状态、BusinessService执行门槛。复用既有审批和幂等账本。

验收：不只是摘要，必须有对象/动作/金额或数量及依据；不通过规则或冲突的卡片清晰标记人工处理；客服改价不改原输出；拒绝、补证及人工接管沿用原会话；客户同意不等于批准；方案更新使旧确认/审批失效；API越权和重复执行被阻止；一笔真实模拟账本及客户回执可回读。

### P4 复杂度路由与独立协作

路径：普通案走单Agent；复杂案事实与政策各自取证→反例核验发现标签编号歧义→只补查事实角色→更新依赖结论→决策卡。

改动：复杂度与金额风险分开记录；强单自主多步/工具并发；新graph显式版本，事实和政策首轮并行及各自工具权限；结构化主张、反证和补查任务；依赖失效、预算原子预留、未知调用不盲重发。

验收：高金额普通案仍单Agent但严格审批；缺一图定向补证；多个商品/包裹或冲突进入多Agent；单Agent发现冲突升级不丢证据；首轮看不到对方意见；只重查有关角色，未过期结果复用；不用投票/自报置信度裁决；超预算/超时转人工，不降级核验标准。模拟物流/仓储数据显式标源。

### P5 三基线、消融与真实端到端

三臂：强单Agent自主调查；单Agent调查/政策/核验三阶段；独立取证+反例+局部补查多Agent。先固定同一模型、相同原始消息/图片/业务政策/工具能力及可比预算，再独立研究模型路由。

普通与复杂冲突分别报告；增加去独立取证、去反例核验、去局部补查的消融，其他条件保持。保留全部失败/超时/未知费用，不只报告优势样本。强单效果相近且便宜则默认简单路径。

指标：动作/金额/补证与客服的一致率（标记非准确率）；独立复核正确/可接受率（多合理方案）；错误候选放行率=错误候选未被拦截/独立判错候选，正确候选误拦率=正确候选被拦/独立判对候选；关键事实遗漏、政策适用/引用；补查前后纠错及引入错误；人工接管；调用次数、端到端/活动耗时及成本。无独立标签时相应分母为0/结果不可用，不能以程序通过代替。

冻结客服介入前输入及Agent输出；独立人员先提交判断再显示建议，记录暴露；客服有新增信息的变更单列。新视觉/协作评测使用新版本数据，不重标历史v0.2结果为新架构成绩。

验收：真实API、真实图片模型传输、真实队列/对象/数据库、浏览器同案链路；普通案和能看到反例纠错的复杂案各一条。五分钟仅面试演示参考，不再是业务正确性/项目完成门槛。旧871.64秒报告保留测量事实，不继续以超时阻断完成。
