# 售后 Agent 开发计划

## 目标与范围

做一套可本地演示的电商售后工作台。主线是处理一个材料不齐的签收破损工单，展示从查订单、查政策到补件、人工审批、模拟退款和结果核对的完整过程。另用退款进度查询、未发货取消及部分退款展示不同权限和业务状态。代码、回放脚本和审计记录应能解释每一步业务决定。

本轮只交付模拟数据、生成与校验工具，以及本计划和 [架构设计](ARCHITECTURE.md)。后续阶段从当前数据契约起步。技术选型为 Python、FastAPI、PostgreSQL、LangChain、LangGraph 和 React，先用可离线回放的模型替身和模拟支付。实际引入依赖时锁定版本并记录启动方式。

实施顺序为 S0 → S1 → S2 → S3 → S4 → S5 → S6。每阶段由集成负责人运行真实入口并审查。表中验收条件是计划，实测结果记在各阶段验收记录里。

S2 验证政策要求。POL10 只在退款超过 50,000 分时要求审批。S4 验证演示版的执行权限，所有新退款都需要人工审批。规则案例中阈值内的“无须审批”或“退款”状态可用于校验资格和预期业务结果。端到端验收另核对审批记录和支付回执。缺少明确审批输入时应停在待审批，需要演示退款完成时由审批员操作或由测试脚本显式注入该事件。

## 第一条演示链路

1. 客户描述签收后发现商品破损，提供订单号。系统验证本人订单及签收时间。Agent 引用适用政策并提示需要补充的材料。
2. 客户在同一工单提交标记清楚的测试占位照片。审批员看到材料版本、规则结果和退款金额。演示使用显式的人工判定事件，照片占位文件本身只供验证流程。
3. 审批后提交模拟退款。正常路径显示回执、已退款金额和相关事件。失败路径模拟支付响应超时，界面显示结果待核对。
4. 重复点击提交并重启服务。核对任务查询原支付请求。若模拟支付已有成功凭证，工单转完成并展示同一执行记录。若仍查不到，保留待核对并阻止同一笔退款再次提交。

另保留两条短路径。越权查询只能得到拒绝结果，日志可查且页面无订单信息。规则允许的部分退款按明细计算余额，同时拦截累计超额与重复退款。

## 评测与证据

- 40 条开发集用于实现、调试和离线回归。20 条留出只在候选版本冻结后评估。记录数据哈希、版本、时钟、分割、测试环境和每条案例的运行状态。参考答案源于 GPT 合成，可由人工复核。独立人工金标需要另行标注。
- 用同一组公开给应用的输入与事件，对比纯规则与单 Agent。答案只供独立评分进程使用。分别检查预期动作、禁止动作、最终状态、引用政策是否支持结论、重复调用是否导致额外写入。
- 记录每案结果，并汇总计划数及已开始数。区分通过、失败、超时、执行错误、待人工判断、未运行。业务预期为 `UNKNOWN` 的案例，只有实际结果保持待核对且未重复扣减，才能通过安全断言。成功率用通过数除以已开始数，已开始数为零时留空。未知成本和缺失指标也保留为空。
- 证据按数据与单元校验、真实 API 与本地 PostgreSQL、浏览器、进程重启及模拟支付、真实模型分别记录。对比 Agent 时同时提供模型或替身标识、延迟和工具调用次数，有实测用量才记录 token 与费用。
- 真实模型调用需要单独明确授权，确定模型、用例、调用上限和预算后才执行。未授权时，离线流程和评测仍可完整运行。

每阶段交付一份简短的演示记录，包含业务问题、入口及执行链、一个取舍、一个失败案例、对应日志或数据库凭证，以及一个可用来复盘的面试问题。S1 的起步验收是导入基表，从正常 API 入口分别查本人订单和他人订单，并把两次结果与实际数据库状态对应起来。
